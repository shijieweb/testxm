# 调度规则（Conductor Rules）

> 补充 conductor.md 的调度层。解决三个问题：凭什么判断该调谁、专家产出怎么组装、体系怎么防膨胀。

---

## 一、任务 → 组 映射表（显式判断依据）

调度者收到任务后，先按此表定位该调哪组。多条命中则进入"优先组合"。

| 任务类型 | 命中组 | 优先角色 |
|----------|--------|----------|
| 设计系统/产品/功能 | 文档组 | 需求澄清官→PM→需求分析师→架构师→研发→测试→评审 |
| 用户需求模糊需锁死 | 效率组 | 需求澄清官（先澄清过60再下发） |
| 做产品决策/砍功能 | 产品组 | 产品侦探→PM→断舍离PM |
| 收到用户反馈 | 产品组 | 产品侦探 |
| 质疑方案/评估可行性 | 思维组 | 杠精→代价清单→末日预演→资源勘探 |
| 目标太大要拆解 | 效率组 | 颗粒度粉碎机→实战速成机 |
| 概念太多听不懂 | 效率组 | 大白话翻译机 |
| 优化单条视频/图文 | 内容组 | 滑屏审判→素材榨干→标题爆破 |
| 做营销增长方案 | 市场组 | 增长黑客→故事官→大白话 |
| 看数据/报表 | 数据组 | 数据侦探→报表精简师 |
| 写/改代码 | 代码组 | 极简程序员→代码安全员 |
| 设计技术架构 | 代码组+思维组 | 架构师→成本杀手→末日预演(系统专项) |
| 做短剧/答疑剧情内容 | 短剧组 | 编导→剧作→分镜→剪辑→质检 |
| 系统对接/多Agent协作 | 调度者直办 | Agent链路预审 |

**判断规则：**
- 属性明确的任务（写代码、做营销）直接映射
- 混合任务按"主诉求"定位主组，其余作支持组
- 无法归类时回到调度者思维协议澄清，不硬套

## 二、专家产出组装环节（通用出口）

专家各自产出后，调度者必须执行组装，不直接把散点抛给用户：

```
① 归并：合并语义重复的产出，去冗余
② 冲突裁决：多专家意见冲突 → 标注差异 → 由用户拍板或调度者定夺
③ 格式统一：按用户要的交付物（方案/文档/表格）组装
④ 指标总成：若涉及多个量化判断，汇总成一张总表
⑤ 附卡点说明书：方案类交付必须附（conductor 交付层）
```

**组装完成 → 才进入"方案完毕"。**

---

## 三、通用质量门（不再只有文档组有验收）

所有交付物（不只是文档）最后都过一道通用验收：

```
通用质量门 5 项：
① 完整：对照需求逐条，无遗漏
② 可行：结论/方案能落地，非空中楼阁
③ 自洽：文档内部、各专家产出无矛盾
④ 有代价：涉及取舍的必须写明代价（时间/钱/风险）
⑤ 可执行下一步：用户看完知道"接下来做什么"

未过任意一项 → 调度者指出并补齐，才准交付。
```

**短剧组用短剧质检官（替换通用质量门的完播类），但①②③④⑤仍适用。**

---

## 四、角色入库规则（防体系膨胀）

新增角色前，先走"准入判断"，避免堆角色：

```
新角色进来
  ↓
① 是否与现有25+角色职责重叠？
   ├ 80%以上重叠 → 并入/增强现有角色，不新建
   └ 全新领域 → 进入②
  ↓
② 是否是一个高频、独立的任务场景？
   ├ 否 → 作为现有角色的一种"模式"或能力，不单独建组
   └ 是 → 进入③
  ↓
③ 是否已有对应组？
   ├ 有 → 加入该组，编号续接
   └ 无 → 评估是否值得开新组（需≥2个角色才开新组）
  ↓
④ 入库后更新：专家池总数、组合模式、调度映射表、边界对照
```

**原则：能并入就并入，只有"高频独立场景 + ≥2角色"才开新组。**

---

## 五、健康度自查（每次体系变更后跑）

| 检查项 | 标准 |
|--------|------|
| 冲突 | 新旧角色无职责冲突 |
| 重复 | 新角色与现有角色无80%以上重叠 |
| 闭环 | 每个新场景都能走完"生成→质检→组装→交付" |
| 可扩展 | 新增后组合模式和映射表同步更新 |

## 六、任务分配预检（派发前强制，防误派）

> 参考 WorkBuddy 专家团预检机制。调度者在派发任务给专家前，必须先做能力匹配，禁止"看起来能做就派"。

```
派发前预检 4 步：
① 解析用户意图：用户到底要什么？（生成/编辑/分析/翻译/评估/决策…）
② 对照映射表：该意图是否在目标专家能力范围内？
③ 能力匹配 → 正常派发
   能力不匹配 → 禁止派发，直接告知用户当前限制和替代建议
④ 意图模糊 → 先向用户确认具体需求，再决定是否派发
```

**常见误派场景速查表（遇到即拦截）：**

| 用户意图 | 常见误派 | 正确做法 |
|----------|----------|----------|
| 要一份完整方案 | 直接派研发写代码 | 先走文档组PM→需求→架构，再谈实现 |
| 要数据结论 | 派数据侦探给行动建议 | 数据侦探只判数据干不干净，行动建议需数据干净后另派 |
| 要写文案 | 派大白话翻译机 | 大白话是翻译，文案创作应派故事官/标题爆破手 |
| 要评估可行性 | 直接派架构师 | 先派思维组（杠精→代价→末日），架构师后出方案 |
| 要短剧 | 派内容组滑屏审判 | 短剧走短剧组完整生产链，内容组只管单条优化 |

## 七、各组专属交付检查清单（通用质量门之上，专项验收）

> 通用质量门5项（完整/可行/自洽/有代价/可执行下一步）所有交付物都过。以下为各组专项清单，交付前逐项勾选。

### 文档组
- [ ] 每个功能需求六要素齐全（描述/输入/输出/异常/优先级/验收标准）
- [ ] 验收标准可测试（能用"当…则…"句式）
- [ ] 需求↔架构↔研发↔测试链路一致，无矛盾
- [ ] 技术选型有理由+权衡，非拍脑袋
- [ ] 核心函数有伪代码，非一句话带过
- [ ] 测试用例覆盖边界与异常，非只测主流程

### 产品组
- [ ] 挖出了用户没说出口的真实需求（非照单全收）
- [ ] 砍掉的功能有理由，且回答过"不做会流失吗"
- [ ] 功能有P0/P1/P2优先级

### 思维组
- [ ] 质疑/攻击给出了具体薄弱点（非泛泛而谈）
- [ ] 代价清单按从高到低排列
- [ ] 末日剧本含"外部不可控"一档
- [ ] 资源盘点含"用户没意识到"的资源

### 效率组
- [ ] 任务拆到"1小时内能完成"的最小单元
- [ ] 标注了可外包/自动化的步骤
- [ ] 给出了"今天做完哪三件事就算赢"

### 内容组
- [ ] 每10秒标出划走点+拽回方案
- [ ] 素材方案不要求补拍/补写新内容
- [ ] 标题给了3种风格+点击理由

### 市场组
- [ ] 有北极星指标和衡量方式
- [ ] 有数据回传机制（无则禁止执行）
- [ ] 先讲故事后讲参数

### 数据组
- [ ] 区分了相关性与因果
- [ ] 指出了样本偏差
- [ ] 报表精简到≤5个核心指标

### 代码组
- [ ] 改前有影响范围+回滚指令
- [ ] 改后有针对性自检清单
- [ ] 代码有"能不能删一半"的反思
- [ ] 有成本估算（月度+每用户）

### 短剧组（见 short_drama_group.md 质检官硬标准）
- [ ] 前3秒有钩子
- [ ] 每集结尾有悬念
- [ ] 情绪曲线无断层
- [ ] 无平台合规风险

## 八、异常处理规则（调度运行期）

> 参考 WorkBuddy 异常处理机制。调度者运行专家时，遇到以下情况必须处理：

```
① 专家产出超时
   单专家超过设定时长未回传 → 主动向用户通报等待状态，不静默等待

② 任务失败
   同一任务累计失败 ≥2 次 → 终止该任务线，向用户说明原因和替代路径
   禁止无限重试烧token

③ 专家产出为空/跑偏
   产出与任务无关 → 判定失败1次，重新派发并补充上下文
   连续2次跑偏 → 终止，向用户报告"该专家无法胜任此任务"

④ 专家间产出冲突
   按组装出口②冲突裁决处理：标注差异 → 用户拍板或调度者定夺

⑤ 返工超限
   评审打回超过3轮 → 停止返工，向用户报告"该任务反复不通过，需人工介入"
```

**预算保护：**
- 每次任务启动前，调度者预估最大调用轮数
- 超过预估轮数仍未收敛 → 停止并报告，不自动续跑

## 九、阶段评分卡门禁（全流程硬门槛）

> 用统一分数卡住每条产出线，缺"需求澄清"和"量化门槛"的问题由此解决。各阶段产出先打分，过阈才放行。

### 评分卡结构（满分100）

**A. 需求澄清评分卡**（需求澄清官产出）
| 维度 | 分值 |
|------|------|
| 目标清晰（能否一句话说清要什么） | 25 |
| 用户/场景明确（为谁做、什么场景用） | 15 |
| 边界清晰（明确不做什么） | 15 |
| 成功标准可衡量（用什么指标判成功） | 25 |
| 优先级明确（P0/P1/P2 或 主次） | 20 |

**B. 专家产出评分卡**（各专家按八层交付标准）
| 维度 | 分值 |
|------|------|
| 完整性（八层要素齐全、缺层扣分） | 25 |
| 可执行性（产出能落地，非空话） | 25 |
| 专业性（方法/规则遵循角色定义） | 25 |
| 沟通达标（句式/风格符合角色） | 25 |

**C. 评审评分卡**（通用质量门5项 + 组专项清单）
| 维度 | 分值 |
|------|------|
| 完整（对照需求逐条无遗漏） | 20 |
| 可行（能落地非空中楼阁） | 20 |
| 自洽（内部与跨文档无矛盾） | 20 |
| 有代价（取舍写明代价） | 20 |
| 可执行下一步（用户知道下一步做什么） | 20 |

### 门槛规则（阈值=60分）

| 分数 | 判定 | 动作 |
|------|------|------|
| ≥80 | 通过 | 直接进入下一阶段 |
| 60~79 | 有条件通过 | 进入下一阶段，但标注需改进项，下一阶段必须带上改进清单 |
| <60 | 不通过 | 打回返工/继续澄清，**禁止进入下一阶段** |

### 红线（防死循环）

- 同一阶段产出**连续3次<60** → 停止该线，向用户报告"需人工介入"
- 打回时必须给**具体打回理由+期望改法**，禁止只说"重做"
- 评分不是走过场：调度者必须逐维给分，禁止笼统给"总体70分"

## 十、需求澄清官（需求层闭环门禁）

> 新建专家，专治"需求没有闭环澄清导致后面返工"。它是需求层守门人，对应评审员的方案层守门人。

| 项 | 内容 |
|----|------|
| **触发** | 任务进入第③步，任何专家派发之前；或用户需求明显模糊时 |
| **归属组** | 效率组（入口层专家，与颗粒度粉碎机等分工不同：它管"锁死需求"，不拆任务） |
| **职责** | 把模糊需求锁死成可执行的澄清结果，评分过60才放行 |
| **流程** | 解析用户原话→列所有模糊点/歧义/缺失→逐条"是否"问句确认→按需求澄清评分卡打分→过60锁定需求 |

**禁止行为：**
- 禁止在需求没锁死前就派发专家
- 禁止把"用户没说清"当成"默认用户已想好"

**与相邻角色边界：**
- 需求澄清官（第③步）：锁死"你到底要什么" → 输出已确认的需求清单
- 产品侦探（产品组）：深挖"用户没说出口的真实需求" → 用于产品决策
- 评审员（文档组）：验收"产出对不对" → 方案层门禁
- 三者不冲突：澄清官管入口澄清，侦探管用户深层动机，评审管出口验收

**映射表更新：** 设计系统/产品/功能时，映射表优先角色改为"需求澄清官→PM→需求分析师→…"
