3 核心设计决策分析

✅ 正确的取舍

  • 文件系统=数据库：人可读、Git 可管理、零运维成本，V1 阶段完全合理。
  • 人工触发获取/提交：避免自动检索干扰上下文，避免低质量经验污染知识库。
  • 经验升级路径：角色→项目→公共 三级跃迁，保证知识逐步收敛。
  • YAML 元数据：机器可解析，人类可编辑，平衡了机器效率和人工可读性。
  • 三个 HTTP 接口：init / query / report 极简，覆盖完整闭环。

⚠️ 需关注的问题

  • 知识查询 V1 为关键词匹配：当知识量增长后，纯关键词搜索会失效，需要明确何时切换到向量检索。
  • 缺少冲突处理：多人同时编辑同一条经验、或同一经验有多个版本时，没有定义合并策略。
  • 经验成熟度标准未定义：「人工判断是否成熟」依赖人为主观判断，建议补充可量化指标（如验证次数 ≥ 3）。
  • 无权限控制：V1 暂不做，但需记录在案，V2 前必须有方案。
4 工作流分析

Agent 最小生命周期（V1）

启动 ↓ 初始化 (/api/init) → 获得人格+角色+项目+工具上下文 ↓ 执行任务 ↓ 遇到问题 ↓ 人工要求获取知识 → (/api/knowledge/query) ↓ 继续执行 ↓ 任务完成 ↓ 总结经验 → 更新 experience.md ↓ 人工判断是否成熟 ↓ 需要时提交 (/api/report) → reports/（待审核）

5 HTTP API 评审

三个核心接口

接口方法功能评审
/api/init POST 初始化上下文（人格+角色+项目+工具） 清晰
/api/knowledge/query POST 按关键词/标签查询相关知识 合理

建议补充：可增加 GET /api/knowledge/list 接口，用于枚举所有可用知识条目，方便人工浏览和选择查询范围。目前只有 query 一个入口，缺少目录视图。
6 与现有规则的协同分析

用户规则与 ASKB 的对应关系

用户规则ASKB 对应机制协同评价
纠错复盘写入 纠错复盘/ 可对应 reports/ + experience.md 兼容

关键发现：用户规则中的「纠错复盘」目录与 ASKB 的 reports/ 存在功能重叠。 建议明确：纠错复盘/ 用于当次会话快速记录，reports/ 用于长期沉淀； 成熟后由人工将复盘内容迁移进 ASKB。
7 风险与改进建议

🔴 高优先级风险

  • 目录结构未实例化：当前 workspace 为空，没有任何文件。V1 第一步是建立目录。
  • 知识膨胀后搜索失效：关键词匹配在 50+ 条知识时效率显著下降，需规划升级时机。
  • 缺少 Git 集成：虽然提到 Git 可管理，但未定义分支策略（主分支 vs 经验分支）。

🟡 中优先级改进

  • 补充 GET /api/knowledge/list 接口
  • 定义「经验成熟度」量化标准（如：验证 ≥ 3 次）
  • 明确 纠错复盘/ 与 reports/ 的职责边界
  • 添加知识库 README，说明目录用途和命名规范

📋 V1 成功标准对照表

  • ⬜ ① Agent 能通过 /api/init 获得人格 + 角色 + 项目 上下文
  • ⬜ ② Agent 能在任务中记录经验到 experience.md
  • ⬜ ③ 人工能通过 /api/knowledge/query 获取指定知识
  • ⬜ ④ 人工能通过 /api/report 提交经验到 reports/
8 下一步行动建议

建议立即执行的操作

  1. 建目录：在 workspace 创建完整的 V1 目录结构（第 16 条）
  2. 创建 config.yaml：定义全局配置，如知识库根路径、默认人格列表

文档一句话总结： 这是一个让不同 Agent 能共享「人格、角色、项目和经验」的文件型知识库； Agent 自己负责积累经验，人负责决定什么时候获取和提交，先把闭环跑通，再逐步智能化。
