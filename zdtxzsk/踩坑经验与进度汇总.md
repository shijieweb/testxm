## 一、踩坑经验全览（按严重程度排序）

### 🔴 高严重度问题

#### 1. find_knowledge_files 搜索结果不过滤（Bug #1）

**现象**：搜索"隐藏关键词"时返回了所有 .md 文件，而非仅匹配文件。

**根因**：`results.append()` 没有 `if match:` 保护，`match` 变量设置后未被消费。

```python
# 错误代码（已修复前）
match = False
if query_lower in fpath.name.lower():
    match = True
elif query_text in content[:200]:
    match = True
# ...
results.append({...})  # ← 缺少 if match: 保护！
```

**修复**：在 `results.append()` 前添加 `if match:` 条件。

**预防**：
- TDD 必须写 negative tests（验证"不应返回"的场景）
- Code review 重点关注「设置标志变量但忘记使用」的模式
- GREEN 阶段验证结果语义正确性，不能只看测试通过

---

#### 2. bare except 吞掉所有异常（Bug #2）

**现象**：服务器运行时某些异常被静默吞掉，无法定位问题。

**根因**：多处使用 `except:`（裸捕获），在 Python 中这会捕获 `BaseException`（包括 KeyboardInterrupt、SystemExit）。

**修复**：
- 所有 `except:` 替换为 `except Exception as e:`
- 每个 catch block 添加 `logger.warning/error()` 日志
- 新增 `_parse_frontmatter()` 专门处理 YAML 解析异常

**预防**：
- CI 中加 pylint/bandit 规则禁止 bare except
- 代码规范文档明确禁止 `except:` 裸捕获

---

#### 3. audit-log 并发覆盖（Bug #3）

**现象**：多 Agent 同时提交经验时，后写入的覆盖先写入的。

**根因**：`read + prepend + write` 非原子操作，两个并发请求可能读到相同内容后各自写入。

**修复**：
- 添加 `_get_lock()` / `_release_lock()` 工具函数
- 使用 `dict[str, threading.Lock]` 管理 per-resource 锁
- `/api/report` 中 audit-log 读写包裹在 lock 内
- config.yaml 增加 `server.lock_timeout` 配置项

**预防**：
- 所有共享写资源统一用 `threading.Lock` 保护
- TDD 阶段补充并发测试（多线程同时调用 /api/report）

---

#### 4. pytest 跨文件 KB_ROOT 污染（Bug #4）

**现象**：`test_shortdrama_knowledge.py` 单独运行 15/15 通过，与 `test_askb_server.py` 合并运行时 6 条搜索测试失败。

**根因**：`test_askb_server.py` 的 fixture 修改了共享的 `askb_server.KB_ROOT`，pytest 执行顺序不确定导致 cleanup 时机不可靠。

**修复**：
- 在每个搜索测试方法入口处显式调用 `askb_server.KB_ROOT = KB_ROOT`
- 添加 `_ensure_kb_root()` 辅助函数
- 模块加载时做一次初始设置作为第二道防线

**预防**：
- 每个测试文件对自己的前提条件负责，不假设全局状态
- 定期全量运行 `pytest tests/`，不要只跑单个文件
- 共享模块状态是集成测试的最大隐患

---

### 🟡 中严重度问题

#### 5. init context 被截断（P1 修复）

**现象**：`/api/init` 返回的 context 被截断到 4096 字符，丢失了偏好记录和进度信息。

**根因**：`max_context_chars` 默认 4096，但实际 context 需要约 4958 字符。

**修复**：`config.yaml` 中 `max_context_chars` 从 4096 改为 6000。

**预防**：配置值应基于实际测量值 + 安全余量（当前 4958 + 1042 = 6000）。

---

#### 6. audit-log 格式混乱（手动编辑导致）

**现象**：手动编辑 `history/audit-log.md` 后，条目出现在 `# 审核日志` header 之前。

**根因**：prepend 逻辑不检查文件原始格式。

**修复**：
- 清理 audit-log.md，恢复正确格式
- 去重逻辑从文件名匹配改为 agent/role 键匹配

**预防**：
- 禁止手动编辑 audit-log.md，所有更新走 /api/report
- server.py 首次写入时检查并重建 header

---

#### 7. YAML frontmatter 解析误报（P3 修复）

**现象**：3 个文件（kb_optimization_plan.md、纠错复盘/*.md）出现 "解析 YAML 元数据失败" 警告。

**根因**：这些文件正文中包含 `---` 水平分割线，被误认为是 frontmatter 分隔符。

**修复**：新增 `_parse_frontmatter()` 函数，仅当文件以 `---` 开头时才尝试解析。

**预防**：frontmatter 解析应检查文件开头，而非简单 split。

---

#### 8. e2e 测试脚本字段名不匹配

**现象**：e2e_full_process.py 首次运行 34/40 通过，6 项失败。

**根因**：测试脚本基于猜测编写，与 server.py 实际响应字段名不一致。

| 失败项 | 原因 | 修复 |
|--------|------|------|
| `has entries(entries=0)` | API 返回 `items` 而非 `entries` | 修正字段名 |
| `report已写入(saved=)` | API 无 `saved` 字段 | 改为检查 `path` |
| `audit已记录` | audit 是副作用不返回 | 改为检查文件内容 |
| `最新记录含 WorkBuddy` | 日志用小写 `workbuddy` | 大小写不敏感匹配 |
| `config/personas/director.md size=0` | 文件不存在 | 补建 director.md |
| `report 文件存在(found=0)` | glob 顺序错误 | 修正为 `*20260822*director*.md` |

**预防**：API 契约必须文档化（openapi.yaml），测试脚本据此编写。

## 三、关键决策记录

| 决策 | 选项A | 选项B | 选择 | 理由 |
|------|-------|-------|------|------|
| 数据存储 | SQLite | Markdown + YAML | Markdown | 易读、版本可控、无需额外依赖 |
| 搜索方式 | 向量检索 | 关键词匹配 | 关键词 | V1 简洁，V2 升级 |
| 并发保护 | Redis 分布式锁 | threading.Lock | threading.Lock | 单机部署，足够 |
| 配置管理 | 环境变量 | YAML 配置文件 | YAML | 可读性好，支持注释 |
| 测试策略 | 手工测试 | TDD | TDD | 61用例保障质量 |

## 四、给下一个 Agent 的建议

1. **启动第一步**：必读 `偏好记录.md` 和 `当前进度.md`，了解行为规则和当前状态
2. **修改 server.py 前**：先读 `docs/openapi.yaml` 确认 API 契约
3. **遇到 Bug 时**：先看 `纠错复盘/` 目录，类似问题可能已记录
4. **添加新知识**：遵循 YAML frontmatter 格式，scope 选 tools/common/projects
5. **运行测试**：每次改动后 `python -m pytest tests/ -v`，确保 61 用例全绿
6. **提交经验**：用 `/api/report` 而非手动写入，确保 audit-log 自动更新

## 五、已知限制（V1 范围）

1. 搜索仅匹配文件名 + 内容前200字符，深层内容不可搜
2. 无向量检索，相关性排序基于匹配位置
3. 无权限隔离，所有 Agent 共享同一知识库
4. 无自动经验触发，需手动调用 /api/report
5. knowledge/ 目录需要手动维护，无自动迁移机制

*以上限制已在 V2 规划中列出改进方案。*
