## 一、前端开发踩坑（TDD / 测试 / 配置）

### 坑 1：Tailwind CSS v4 配置问题（PostCSS 插件报错）

**现象**：启动/构建时报 PostCSS 插件错误，Tailwind 无法正常编译。

**根因**：项目使用 Tailwind CSS v4，v4 采用新的 `@tailwindcss/postcss` 插件，与 v3 的 `tailwindcss` 插件不兼容；且 v4 用 `@theme` 指令替代 v3 的 `tailwind.config.js` 主题配置。

**解决**：
1. 安装 `@tailwindcss/postcss`
2. `postcss.config.js` 使用 `@tailwindcss/postcss` 插件
3. `index.css` 改用 `@import "tailwindcss"` + `@theme { ... }` 定义主题变量

**经验**：Tailwind v4 与 v3 配置差异大，升级/新建项目时先确认版本再配置。

### 坑 2：React 测试中 disabled 按钮不触发 onClick

**现象**：测试中 `fireEvent.click` 点击 disabled 按钮，onClick 不执行，测试失败。

**根因**：React 的 `fireEvent.click` 不会触发 disabled 按钮的 onClick（浏览器原生行为）。

**解决**：改用原生 `dispatchEvent(new MouseEvent('click', { bubbles: true }))` 触发。

**经验**：测试 disabled 状态时，用原生事件派发而非 fireEvent。

### 坑 3：测试选择器匹配歧义

**现象**：`getByText` 匹配到多个元素报错（如 MainLayout 中"设置""创建"文本在侧栏和底部导航重复出现）。

**解决**：先检查元素数量（`getAllByText`），再用更精确的选择器（CSS class、role、data-testid）。

**经验**：布局组件中重复文本很常见，测试时优先用 `getAllByText` + 数量断言，或加 `data-testid`。

### 坑 4：lucide-react 图标在测试环境报错

**现象**：测试中 lucide-react 图标渲染 SVG 导致 jsdom 报错或测试不稳定。

**解决**：在 `vitest.setup.ts` 中统一 mock 全部用到的图标，返回简单的 `<svg>` 元素并加 `data-testid`。

**经验**：第三方 UI 图标库在 jsdom 测试中常出问题，统一 mock 是标准做法。

### 坑 5：导入路径错误

**现象**：设置页组件导入路径错误，报模块找不到。

**根因**：路径中多了不必要的 `components/` 目录层级。

**解决**：修正为正确的相对路径。

**经验**：重构目录后要同步检查所有导入路径。

### 坑 6：多行内容断言失败

**现象**：PromptTemplatesCard 测试中，多行模板内容用精确字符串断言失败。

**解决**：用正则匹配（`expect(...).toHaveTextContent(/.../)`）而非精确匹配多行字符串。

**经验**：多行文本断言用正则，避免空白/换行差异导致失败。

### 冷启动检查踩坑（ISSUE-009 ~ 011）

| 编号 | 问题 | 严重度 | 状态 |
|---|---|---|---|
| ISSUE-009 | **git 仓库未初始化（P0）**——闭环 5 入库流程的"git commit 可回滚基线"和"版本回滚"完全失效 | P0 | 已解决 |
| ISSUE-010 | 闭环 1 自审记录格式缺列（缺日期/场景描述） | 中 | 已解决 |
| ISSUE-011 | 计数器表与活动日志不一致（显示 7 实际 8） | 中 | 已解决 |

**ISSUE-009 详解（最重要）**：体系规则要求"每次入库前 git commit 作为可回滚基线"，但实际 `.team` 目录从未初始化 git 仓库，`git status` 返回 "fatal: not a git repository"。这意味着所有"修改前已备份到 git"的声明都是空的，ANGLE-019 可逆性原则失去技术保障。修复：`git init` + 配置 user.name/email + 首次基线提交 + js-end.sh 自动 commit + js-start.sh `--check` 改 FAIL。

**核心教训**：**声明了机制不等于机制真的存在**。规则写"已备份到 git"但 git 从未初始化，就是"形式合规实质失效"（DET-002 的典型场景）。任何依赖外部基础设施的机制，必须先验证基础设施真实存在。

### DET 规则与角度库踩坑（ISSUE-012 ~ 015）

| 编号 | 问题 | 严重度 | 状态 |
|---|---|---|---|
| ISSUE-012 | ANGLE-024 规则臃肿（10 条中 8 条是 DET 引用）+ DET 清单冗余 | 高 | 已解决 |
| ISSUE-013 | 候选 ANGLE-025 与 DET-002 内容重叠，无增量价值 | 中 | 已解决（拒绝入库） |
| ISSUE-014 | DET 融合方案来回讨论 3 轮才落地，根因是提案流程缺"前置检查" | 高 | 已解决 |
| ISSUE-015 | 三个硬障碍修复（git 初始化 + DET-002 自动化 + 缓存 hash 校验） | 高 | 已解决 |

**核心教训**：
- 提案流程必须先做"前置检查"再提交，不能从"分析"直接跳到"提交"
- 审查他人方案的能力 ≠ 自己提案时的自我审查能力（军师审查 6/6 命中，但自己提案时同样犯 DET-002 错误）
- 凡是有机器可执行路径的保障，优先脚本执行，不靠自觉（缓存 hash 校验由脚本层执行）

## 三、经验沉淀（已固化为规则）

### 3.1 DET 检测项（14 条，防再犯）

团队体系把踩坑经验固化为 DET（Detection）检测项，执行任务前逐条自检。核心几条：

| DET | 检测内容 |
|---|---|
| DET-001 | 提归档方案时必须写回溯路径（怎么找、找什么） |
| DET-002 | 提数字时必须算实际效果/有计算过程，禁止"形式合规实质失效"（如 95%/70% 无计算来源） |
| DET-003 | 提保留数量时算 ≥2 个备选值对比 |
| DET-005 | 提条数时算条数 × 单条平均字数 = 总字数 |
| DET-007 | 规则变更后检查所有引用一致性 |
| DET-010 | 显示窗口对齐实际行数，若远大于窗口改用按结构定位读取 |
| DET-012 | 输出太大时检查上限 + 算总大小 + grep 锚定 |
| DET-014 | grep/正则必须有空返回检查 + 警告输出 + --check 频率 |

### 3.2 认知框架角度（24 个，审视工具）

| 角度 | 核心问题 |
|---|---|
| ANGLE-001 先验自审 | 这个方案/判断，我自己用已有角度验过没有？ |
| ANGLE-005 找盲区 | 还有什么没考虑到？ |
