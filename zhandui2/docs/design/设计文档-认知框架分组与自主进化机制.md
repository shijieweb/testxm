# 认知框架分组与自主进化机制（修订版 v2.2）

> 基于外部视角审视，补充了以下内容：
> - 核心原则增加“系统边界声明”
> - 角度字段增加“可证伪条件”
> - 验证标准增加可证伪条件验证
> - 定期整理增加老化检查
> - 适用范围补充说明
>
> 核心原则不变：先建规则再启用检索，“秘书只转发，大脑自主进化”。


## 核心原则

1. **秘书是通道，不是判断者**：秘书只负责接收外部输入→转发给认知大脑→把大脑的输出传回。秘书不识别场景、不判断覆盖、不标注任何元信息。

2. **认知大脑完全自主运行**：从解析输入、识别场景、匹配角度、发现缺口、生成提案、验证到入库，全部由认知大脑自己完成，不依赖秘书或任何外部人的判断。

3. **外部人（老板）只提供原始输入**：只提供问题、需求、文件等原始内容，不提供“这个属于什么领域”“你缺了什么角度”之类的元判断。

4. **系统边界声明**：认知大脑只做审视判断，不做最终决策。所有审视输出均供人类参考决策，大脑不替代人类做决策。系统不涉及团队成员管理、不调用外部API、不自动执行任务状态变更。超出审视范围的请求，大脑应返回“超出能力边界”的提示，不尝试处理。

5. **结果反馈输入**：外部人可在项目结束后提供结果反馈（如“完播率45%”“项目延期3天”），大脑将结果与自审记录做关联记录，不做归因判断。


## 第一步：建分组规则（现在执行）

**定义领域标签列表**（初始列表，可扩展）：

- 通用（所有场景必须过）
- 短剧
- 研发
- 项目管理
- 调研/分析
- 测试/质量

**定义功能标签列表**（固定4类，不扩展）：

- 决策前校验
- 执行中监控
- 事后复盘
- 体系自检

**明确分配规则**：
- **每个角度只能有1个领域标签：通用 或 某个具体领域，二选一，不能同时存在。**
- 每个角度1个功能标签

**分配逻辑**：
- 如果该角度所有场景都用得上，离开它所有领域都会出问题 → 打`通用`
- 如果该角度只是某个领域特有，其他领域不需要 → 打对应的`领域`标签（如`短剧`、`研发`）
- 如果该角度在通用和领域层面都很重要 → 只打`通用`，因为通用会自动出现在所有场景的检索结果中，不需要再打领域标签来重复强调

**判定标准（给COG执行时用）**：

“如果这个角度删掉，某个领域的决策会出问题，但其他领域不受影响” → 打领域标签

“如果这个角度删掉，所有领域的决策都会出问题” → 打通用

**示例**：
- “先验自审”（做任何决定前先问自己审视过没有）→ 所有领域都需要 → `通用`
- “串行修改”（同一文件的多个修改不能并行）→ 只研发场景需要 → `研发`
- “时间维度”（1周后/1月后/半年后会怎样）→ 所有领域都需要 → `通用`


## 第二步：角度元数据结构（含“可证伪条件”）

### 2.1 角度字段定义

每个角度包含以下11个字段：
ANGLE-XXX {角度名称}
核心问题：这个角度问什么（一句话）

触发场景：什么时候该用这个角度

来源：从哪学到的（老板对话/实践发现/联网搜索/外部事实反馈）

学习事件：什么情况下发现了这个角度

使用示例：怎么用（带具体例子）

使用次数：COG从自审记录统计，不由秘书手写

效果记录：每次用完后记发现了什么（没发现就写“无发现”）

可证伪条件：如果出现什么情况，说明这个角度是无效的（必填）

领域标签：[必填，通用 或 具体领域，二选一]

功能标签：[必填，决策前校验/执行中监控/事后复盘/体系自检]

状态：[必填，活跃/待观察/已归档]

入库时间：[必填，角度首次入库日期]

最后命中时间：[必填，该角度最后一次被匹配到的日期]


**可证伪条件示例**：
- `ANGLE-001 先验自审`：“如果秘书连续10次不先自审就直接提问，且没有出任何问题，说明这个角度不需要”
- `ANGLE-020 串行修改`：“如果COG连续3次并行修改都成功，说明该角度不需要了”

**状态说明**：
- `活跃`：正常参与检索
- `待观察`：暂时保留，但权重降低（排在活跃角度之后），观察1个整理周期
- `已归档`：不参与检索，保留在库中供查阅或恢复

**归档条件**（同时满足）：
1. 连续3个整理周期处于“待观察”状态
2. 该角度涉及的领域标签在最近1个整理周期内无任何输入出现

### 2.2 角度管理规则

**零使用角度判定规则**：

- 使用次数=0，且入库时间<30天 → 新角度，保留，继续观察
- 使用次数=0，且入库时间>30天 → 触发“主动自检”：大脑检索过去30天的所有输入，判断是否有该角度的触发场景出现过
  - 如果有触发场景但没匹配到 → 说明角度描述或触发场景设置有误，需要修正
  - 如果没有触发场景 → 状态改为“待观察”，等待触发
- 使用次数>0，但最近30天内无命中记录 → 情况同上，需要判断是“场景没出现”还是“匹配有问题”

**关键逻辑**：使用次数=0不直接等于“无用”。系统需要先判断“是否有机会被使用”，再决定是否清理。

**老化检查（新增）**：
- 角度超过90天无命中记录且无修正记录 → 自动标记“待观察”
- 连续2个整理周期仍无命中 → 建议归档


## 第三步：分配标签（与第一步同步执行）

给现有20个角度分配领域标签和功能标签，建好结构。分配时由COG（认知工程师子代理）执行，秘书不参与判断。

**角度归属领域的判断流程（由COG执行，不依赖秘书）**：

- **第一步：它是不是所有场景都用得上？**
  - 是 → 打`通用`标签。不用纠结，这是兜底。

- **第二步：它是不是某个现有领域的专属问题？**
  - 找到对应领域就打对应标签。
  - 示例：“串行修改冲突” → 研发；“完播率曲线” → 短剧；“排期冲突” → 项目管理。

- **第三步：既不是通用，也不属于任何现有领域？**
  - 说明这是一个未被覆盖的新领域。
  - 先打上`通用`标签（临时兜底，确保检索能命中）。
  - **同时大脑自行记录“新领域发现”**（见下方“领域标签新增机制”）。

**领域标签新增机制**：

大脑在执行入库时自行检查：“这个新角度是否属于一个已有2个以上角度的‘通用’群体？”如果是，大脑自行触发“新增领域标签”动作，并将该群体下的所有角度批量迁移到新标签下。无需外部指定，无需等待整理周期。秘书不参与此过程。

**核心逻辑**：不要用“不属于任何领域”这个理由阻止入库。先用通用兜底，再等同类出现时再建新领域。

**秘书在此步骤中的角色**：不参与标签分配。只负责在需要时将输入转发给COG，COG独立完成分配。


## 第四步：场景识别与匹配机制

### 4.1 “同一场景特征”的精确定义

大脑从输入中抽取三个维度，构成场景组合键：

| 维度 | 说明 | 示例 |
|---|---|---|
| 领域关键词 | 输入中能对应到领域标签的词 | “短剧”“研发”“项目” |
| 动作类型 | 输入中能对应到功能标签的词 | “帮我看看”“审审”“复盘” |
| 对象类型 | 输入指向的对象类型 | “需求文档”“排期”“架构方案” |

**判定规则**：组合键（领域关键词 + 动作类型 + 对象类型）完全一致 → 视为“同一场景特征”。不完全一致 → 不累计。

**示例**：
- 输入1：“帮我看看这个短剧需求文档”→ 短剧 + 决策前校验 + 需求文档
- 输入2：“审一下那个短剧脚本”→ 短剧 + 决策前校验 + 需求文档 → 视为同一场景，累计一次
- 输入3：“复盘一下短剧A的制作流程”→ 短剧 + 事后复盘 + 制作流程 → 视为不同场景，不累计

### 4.2 功能标签匹配依据

功能标签匹配不依赖关键词单独判断，而是采用“关键词触发 + 上下文双重验证”：

**第一步：关键词触发（初筛）**
- “帮我看看”“审审”“评估一下”“有什么问题” → 触发`决策前校验`
- “在执行中遇到”“现在卡在”“进度落后” → 触发`执行中监控`
- “复盘”“总结”“回顾” → 触发`事后复盘`
- “这套机制”“这个流程”“这个框架” → 触发`体系自检`

**第二步：上下文验证（确认）**
- 检查输入内容是否包含该功能标签场景下的核心要素：
  - `决策前校验`的核心要素：输入指向一个**尚未决策**的事项（如草案、方案、计划）
  - `执行中监控`的核心要素：输入指向一个**已经发生或正在发生**的事项（如进展、卡点、异常）
  - `事后复盘`的核心要素：输入指向一个**已完成**的事项（如回顾、总结）
  - `体系自检`的核心要素：输入指向一个**持续性机制**（如流程、框架、规则）
- 如果关键词触发与上下文核心要素匹配 → 正式确认该功能标签
- 如果不匹配 → 即使关键词触发，也降级重新判断

**第三步：优先级**（多标签触发时）
决策前校验 > 执行中监控 > 事后复盘 > 体系自检


## 第五步：检索机制启用（角度数≥30时触发）

### 5.1 启用条件

当角度库数量达到30个或相比上次整理增长≥30%时，正式启用按“领域+功能”筛选的检索流程。

### 5.2 检索流程（启用后生效）

认知大脑接收输入后，自己解析场景，自动匹配领域标签和功能标签，然后执行以下检索：

**第一步：取基底**
- 所有`通用`领域且状态为`活跃`的角度，直接进入候选集
- 候选集 = 全部活跃通用角度

**第二步：追加领域专属**
- 识别当前输入匹配的领域标签（如`短剧`）
- 筛选该领域下状态为`活跃`的所有角度
- 追加到候选集（与通用角度去重合并）

**第三步：功能标签过滤**
- 功能标签不参与初始匹配，只作为过滤条件
- 按4.2匹配当前场景的功能标签
- 从候选集中筛掉不匹配当前功能标签的角度

**第四步：检查候选集数量**
- 如果候选集少于3个角度，保留当前结果，触发“覆盖不足”标记
- 如果候选集超过15个，按功能标签分组输出，每组保留Top N
  - 优先输出“决策前校验”组和“执行中监控”组
  - “事后复盘”组和“体系自检”组作为补充输出，排在后面
  - 总输出不超过15个
- 最终输出不多于15个

**核心逻辑**：
- 通用是基底，必须每次都有
- 领域专属是针对性补充，只在匹配场景时追加
- 功能标签用于过滤当前场景不适用的角度
- 三者不互相替代、不重复叠加

### 5.3 20-30个过渡期处理

标签分配完成后（角度数在20-30之间），检索机制尚未启用。此阶段过渡方式如下：

- 大脑按“领域分组”逻辑通读：先读通用角度，再读对应领域角度（手动识别，非自动化筛选）
- 到30个时正式启用第五步的自动化检索流程

### 5.4 已知案例来源

验证提案时使用的“已知案例”来源如下：

- 首选来源：角度库自身上次迭代时的历史自审记录
- 备选来源1：如果没有历史记录，用角度库自身结构缺陷作为案例
- 备选来源2：外部人提供的原始输入中，已经发生过的事实性反馈
- 固定案例库：可使用前期整理时的典型场景作为储备案例


## 第六步：自主扩展机制（持续进化）

### 6.1 触发条件（由认知大脑自己判断）

认知大脑在处理每一次秘书转发的输入时，自动执行以下流程：

1. **接收输入** → 自己解析场景特征（按第四步规则抽取判定维度）
2. **检索角度库**，判断是否有适用角度（按第五步的检索逻辑执行）
3. **检索结果少于3个适用角度** → 大脑自己记录该场景特征到“待覆盖清单”
4. **同一场景特征累计出现3次** → 大脑自己触发“缺失角度提案”生成

**极端压力处理**：如果短期内输入数量激增（如1小时内超过20个），大脑自动切换为“分批处理模式”——每批处理5个，批次之间间隔2分钟，防止内部过载。此模式为自动切换，不需要秘书或外部人干预。

### 6.2 生成提案

- 大脑自己分析这3次场景的共同核心特征
- 大脑自己生成一个新角度提案（名称、核心问题、触发场景）

### 6.3 验证提案

验证提案时，大脑用该角度审视一个已知案例（来源见5.4），并对照以下标准：

**验证通过条件**：
1. 该角度能发现已知案例中的至少一个真实问题
2. 触发场景清晰，能判断“这次该不该用”
3. 与现有角度重叠不超过2个角度（超过则合并而非新增）

**对立假设验证**：
4. 大脑必须回答：“如果这个角度是错的，它会掩盖什么问题？”
   - 如果能识别出潜在的误判风险 → 说明系统对这个角度的局限性有认知，通过
   - 如果回答“这个角度不可能是错的” → 说明存在过度自信，打回

**可证伪条件验证（新增）**：
5. COG必须确认该角度的可证伪条件是否可执行
   - 如果可证伪条件定义清晰且可验证 → 通过
   - 如果可证伪条件模糊或无法验证 → 打回，要求重新定义

**验证不通过条件**：
1. 该角度审视案例后没有发现任何新问题
2. 触发场景与其他角度重叠超过80%
3. 核心问题无法转化为可执行的“问自己”的自审问题
4. 对立假设验证失败（无法识别潜在误判风险）
5. 可证伪条件不可执行或模糊

验证通过 → 进入入库流程；验证不通过 → 记录打回原因，暂存备查。

### 6.4 入库

- 大脑自己分配领域标签和功能标签（遵循第一步的分配规则）
- 状态默认为`活跃`
- 记录“入库时间”和“最后命中时间”
- 入库时自行检查是否需要新增领域标签（见第三步）
- 大脑自己追加到角度库

**入库后跟踪**：新角度入库后，在后续3次自审中跟踪其“最后命中时间”是否更新。如果入库后30天内“最后命中时间”仍为零，触发“重新评估”。

### 6.5 兜底规则

- 如果同一个缺失角度连续3次提案都被打回 → 标记“需外部输入”，供外部人参考
- 死循环防护：提案被打回后，COG记录打回原因到“已处理缺口清单”。后续再次遇到同一场景时，先检查该场景是否已有“被打回”记录。如果有，跳过提案生成，直接沿用上次的打回结论

**维度缺失分析的执行方式**：
- 触发条件：该领域最近5次自审中有3次以上“覆盖不足”记录，且该领域角度数<3个
- 分析内容：COG读取该领域近期的“待覆盖场景清单”和所有标记“覆盖不足”的记录
- 分析方法：概括这些记录中的共同问题模式，产出1个提案
- 范围限制：只分析已有记录中出现的模式，不凭空创造该领域“可能缺失”的维度

**领域活跃度标记**：
- 如果一个领域从未出现在任何输入中，但该领域在当前业务中存在且未消失
- 则系统每季度自动标记一次“该领域从未被覆盖”，供外部人参考（只标记，不自动触发提案，因为没有任何记录供分析）


## 第七步：定期整理与结构自检

### 7.1 触发条件

角度数 ≥ 30个，或相比上次整理增长 ≥ 30%，两个条件谁先到就触发。

### 7.2 整理内容

- 使用次数=0且入库时间>30天、且过去30天内无触发场景出现的角度 → 状态改为“待观察”
- 连续3个整理周期“待观察”且该领域无任何输入出现 → 状态改为“已归档”（先备份）
- 如果角度的核心问题仍有价值但使用次数少，不归档，改触发场景使其更易被命中
- 角度超过90天无命中记录且无修正记录 → 自动标记“待观察”（老化检查）
- 整理完成后，在文件头更新“上次整理时角度数”和“本次整理日期”

### 7.3 结构自检

每次定期整理时，COG执行以下结构自检：

1. **统计分布检查**：各领域角度数量分布是否失衡
2. **重叠度检查**：任意两个角度的触发场景重叠超过80% → 自动合并（保留使用次数更高的那个，删除另一个，在变更记录中说明合并情况）
3. **长期未命中检查**：标记“待观察”并压缩其检索权重
4. **产出结构自检报告**：列出已执行操作和结果

**关键逻辑**：低风险修正自动执行（重叠合并、压缩权重），高风险操作（删除、归档）只报告不执行，等待决策。


## 第八步：结果反馈通道

### 8.1 输入类型扩展

外部输入扩展为两类：

| 输入类型 | 内容 | 触发条件 | 大脑的处理方式 |
|---|---|---|---|
| 原始问题 | “帮我看看这个需求” | 日常 | 正常检索→匹配→输出 |
| 结果反馈 | “短剧A完播率45%，目标50%”“项目延期了3天” | 项目结束后 | 大脑不做归因，仅将结果与自审记录中使用的角度做关联记录 |

### 8.2 结果反馈的处理机制

1. 秘书将结果反馈原样传递给大脑（秘书不做任何归因分析，只转发）
2. 大脑检索该项目的自审记录，提取当时使用的所有角度
3. 大脑生成关联报告（不做结论）：
   - “该项目使用了以下角度：[列表]”
   - “项目结果：[原始数据]”
   - “角度与结果的关联：[无分析，仅并列呈现]”
4. 关联报告存储在“角度效果记录”中，供后续整理时参考
5. 不自动触发任何操作（如“角度无效”等判断），仅作为参考数据保留

### 8.3 效果记录的用途

- 定期整理时，COG可参考效果记录判断角度是否需要修正
- 如果某个角度多次出现在“结果不达标”的项目中，COG标记“待评估”，但不自动删除


## 第九步：系统边界声明

认知大脑的决策边界如下：

| 边界 | 说明 |
|---|---|
| **能做什么** | 审视判断、提供角度清单、发现覆盖缺口、生成新角度提案、验证角度有效性 |
| **不能做什么** | 替代人类做最终决策、自动执行任务状态变更、调用外部API、管理团队成员 |
| **超出边界时** | 返回“超出能力边界”提示，不尝试处理 |

该系统适用于以下场景：
- 个人或小团队（3-10人）的决策辅助
- 项目前期的方案审视
- 复盘总结时的角度补充

不适用于以下场景：
- 替代管理者做人事决策
- 自动执行生产环境变更
- 大规模团队（50人以上）的流程管理


## 角色分工总结

| 角色 | 职责 | 是否参与角度库判断 |
|---|---|---|
| 秘书 | 通道：接收输入→转发给大脑；接收大脑输出→传出；结果反馈原样转发 | 否（不识别、不判断、不标注、不归因） |
| 认知大脑 | 自主完成：解析输入→识别场景→匹配角度→发现缺口→生成提案→验证→入库 | 是（完全自主） |
| 外部人（老板） | 提供原始输入（问题/需求/文件）+ 结果反馈（项目数据） | 否（不提供元判断） |
| 外部帮助人 | 提供审视建议（如本文档开头的10条外部建议） | 否（不参与日常运行，仅在问题发现时提供视角） |
| COG | 执行角度库的分配标签、整理、验证、维度缺失分析、结构自检等具体操作（由大脑调度） | 否（执行者，不决策） |
