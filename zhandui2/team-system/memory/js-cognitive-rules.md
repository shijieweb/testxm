## 一、角度库生命周期管理

### 新增角度
角度新增有两种路径：
1. **自动路径（生产线默认）**：任务后覆盖检查发现同一场景缺覆盖≥3次 → 自动生成提案 → 自动走验证标准清单5项硬指标 → 全通过自动入库。不需要秘书识别或军师手动判断。
2. **手动路径（当前阶段）**：秘书在对话中识别新角度 → 派发军师 → 军师走验证标准清单5项硬指标 → 通过则入库。等自动路径启用后此路径作为补充。

新增流程：
1. 识别/自动生成：确定角度名称和核心问题
2. 提炼：触发场景、来源、学习事件
3. 识别复核：通读现有角度（<30个）或按标签筛选（≥30个），确认未被覆盖
4. 验证（见验证标准清单）：用5项硬指标逐条对照
5. 追加：写到角度库末尾，编号递增
6. 记录学习事件：把"什么情况下发现了这个角度"写进来源

### 识别复核
秘书识别到新角度后，派发军师前必须先做识别复核：
1. 通读现有角度库（角度数<30时通读，≥30时按领域+功能标签筛选）
2. 确认现有角度未被新角度覆盖（新角度的核心问题与所有现有角度的核心问题都不重叠）
3. 如果发现已被覆盖，不派发军师，改用现有角度
4. 如果确认未被覆盖，派发军师验证

### 验证标准清单
军师验证新角度时必须逐条对照以下五项硬指标，不能凭感觉裁决。全部通过才入库，任一不通过打回：

1. **发现真实问题**：该角度能否在已知案例中发现真实问题？（不能→打回）
2. **触发场景清晰**：触发场景是否清晰无歧义，秘书能判断什么时候该用？（模糊→打回）
3. **非重复**：与现有角度的核心问题重叠>2个字段（核心问题+触发场景+使用示例中2个以上相同）→合并而非新增，在产出说明里写明跟哪个角度重叠、重叠在哪
4. **对立假设验证**：必须回答"如果这个角度是错的，它会掩盖什么问题"。答"不可能错"→打回（过度自信）
5. **可证伪条件验证**：必须写出"如果出现X情况说明这个角度无效"，且X是可观测的。模糊或无法验证→打回

军师验证时无论通过还是打回，产出说明里必须写明：审了哪个案例、五项指标逐项结论、最终决定。

### 灰色地带自动处理（v1.9新增）
验证标准清单5项硬标准的设计原则是"尽量可机械判断，灰色地带走自动打回+标准细化流程"。其中标准2（触发场景是否清晰）和标准4（是否答"不可能错"）相对机械；标准1（发现真实问题）、标准3（非重复）、标准5（可证伪条件验证）含有判断成分，灰色地带按自动打回处理。

1. **自动打回**：灰色地带一律按"不通过"处理（遵循"宁可漏进不可错进"原则）。不等人判断。
2. **记录灰色模式**：将该案例的灰色特征（哪项指标、什么场景、为什么判不了）记录到 `status/gray-areas.md`。
3. **同类≥3次触发标准细化**：同一类灰色模式在 `gray-areas.md` 中累计出现≥3次，军师自动提案验证标准细化——把模糊标准改成更精确的可判断标准。
4. **细化标准自验**：细化后的标准本身也要过可证伪条件验证（"如果出现X情况说明这个细化标准无效"），通过才更新验证标准清单。
5. **变更记录**：每次标准细化必须记录变更前后对比到 `status/standard-changes.md`，包括：哪项标准、原表述、新表述、细化原因、通过率变化。
6. **漂移防护**：如果标准细化后通过率变化超过±15%，自动触发秘书审查，不等下次整理（见 js-cognitive-charter.md 11.5第4道保险）。

### 验证标准自进化（v1.9新增）
验证标准清单不是一成不变的。军师通过灰色地带积累自动细化标准，让硬标准越来越精确：

- **进化触发**：灰色地带同类≥3次（见"灰色地带自动处理"第3步）
- **进化方向**：只能把模糊标准改得更精确，不能把严格标准改宽松。如果细化后通过率上升超15%，触发秘书审查
- **进化记录**：所有标准变更记录到 `status/standard-changes.md`，秘书每次整理时审查
- **回滚机制**：秘书发现标准被放宽，有权回滚到任意历史版本。回滚操作也记录到 `standard-changes.md`
- **进化边界**：5项硬标准的框架不变（发现真实问题/触发场景清晰/非重复/对立假设验证/可证伪条件验证），只细化每项的具体判断标准

### 修正角度
- 发现某个角度在实际使用中不对或不够，直接修改该角度的描述
- 修正记录统一写在文件头变更记录里（见"变更记录归档"规则按版本归档），不在角度描述末尾追加——保持角度描述只反映当前状态，不混历史痕迹

### 使用次数更新
- 秘书每次用角度自审后，在 status/ms-standin-review.md 里写明用了哪些角度编号（只写编号，不写次数）
- 军师整理时读 ms-standin-review.md 统计使用次数，更新角度库
- 不靠秘书自己手写使用次数（防糊弄，呼应ANGLE-008）：秘书只标编号，次数由军师统一统计写入
- 如果 ms-standin-review.md 不存在或该轮没记，该轮使用不计入（倒逼秘书养成记录习惯）
- 当某角度使用次数首次从0变为>0时，军师必须在本次整理中为其补写可证伪条件（此时已有真实使用场景可参照）。"待补"状态的角度在被使用后必须在下次整理时补写，不得继续标"待补"。如果军师判断该角度的使用场景不足以写出可观测的证伪条件，在js-self-review.md写明原因并保留"待补"，但必须在角度效果记录中标注"可证伪条件延期补写，原因XXX"

### 自审记录要求
自审记录（status/ms-standin-review.md）分两档：
- **强制前置**：派发子代理任务前、向老板汇报前、向老板提问前、不可逆决策前——必须先完成自审记录，否则禁止下一步。无例外。
- **事后补记**：执行中的快速判断——允许先判断后补记，但必须在当轮对话内补记完成。

自审记录格式：
- 日期时间
- 场景描述（一句话）
- 使用的角度编号列表（只写编号，不写次数）
- 每个角度的问题+回答+结论（各一句话）

### 角度效果反馈
- 每个项目结束后，秘书在复盘时记录：哪些角度的判断被实际结果证实了、哪些被证伪了
- 被证伪的角度，秘书在项目复盘时把证伪信息写入angle-feedback.md的"标记"字段（标"待评估"），写明什么场景下导致什么错误决策
- 军师整理时读取angle-feedback.md，某角度累计被标"待评估"≥2次→自动标"待修正"，触发"证伪角度自动处理"流程。"自动"=军师整理时执行，非实时自动
- 这是从"用了发现什么"到"用了之后实际结果对不对"的闭环

### 证伪角度自动处理（v1.9新增）
角度累计被标"待修正"≥2次时，军师自动分析根因并处理，不报秘书判断：

1. **根因分析**：军师分析角度被证伪的原因，分三种情况：
   - **核心问题已过时**（该场景不再出现）→ 归档（不删除，保留可逆性），记录归档原因
   - **描述/触发场景有误** → 军师自动重写描述或触发场景 → 5项硬标准重验 → 通过则更新角度，不通过则归档
   - **重验不过** → 归档 → 如果同缺口后续≥3次再出现（闭环2记录）→ 自动从归档区复活重验
2. **归档不删除**：所有处理都走归档不走删除，保证可逆（呼应ANGLE-019可逆性）。归档去向：`memory/.archive/js-archived-angles.md`（专用归档文件，按角度编号排列，不是删是移到归档区保留可追溯）
3. **复活机制**：归档的角度如果对应缺口再次累计≥3次，自动从归档区取出重新验证。防止误归档好角度
4. **处理记录**：每次证伪处理写入 `status/js-self-review.md`，写明：哪个角度、根因分析、处理方式、重验结果

### 系统性偏差检查
军师每次整理时执行系统性偏差检查，检查整个角度库的结构有没有歪。这不是查单个角度对不对（那是验证标准清单和角度效果反馈的事），是查整体偏向。

检查5个维度：

| 维度 | 检查什么 | 预警标准 |
|---|---|---|
| 来源分布 | 角度来源类型是否过于单一 | 单一来源占比>70%预警 |
| 视角分布 | 审视方向是否覆盖足够多视角 | 只有1种视角类型预警 |
| 功能分布 | 四个功能标签是否严重失衡 | 某个功能标签占比>60%或=0预警 |
| 证伪记录 | 有没有被证伪但没标记的角度 | 有证伪记录但角度未标"待修正"预警 |
| 覆盖盲区 | 有没有整类问题完全没覆盖 | 对比已知批判性思维框架，缺整类维度预警 |

执行要求：
- 军师每次整理时逐项检查，结果写进js-self-review.md
- 发现偏差时在产出说明里标"系统性偏差预警"，写明哪个维度、具体数据、建议措施
- 秘书看到预警后决定是否派军师联网搜索外部方法论补充
- 与角度效果反馈（P7）互补：P7查单个角度对不对，系统性偏差检查查整个角度库歪不歪

**走岔了检测（每次任务返回时自动执行，v1.9更新）：**

系统性偏差检查是军师用角度库规则查角度库，本质还是"自己查自己"。如果偏差方向跟检查者一致，发现不了。以下规则用外部锚点打断内部循环：

1. **军师自动查"该有但没有"**：军师每次任务返回时读取 `status/coverage-gaps.md`，自动比对"这次任务中遇到的问题" vs "角度库中能覆盖这些问题的角度"。发现"该有但没有"→记录到coverage-gaps.md。同一场景特征累计出现3次→自动触发闭环3。
2. **Explore独立查同一件事**：秘书派Explore子代理用外部视角独立审"这个项目有没有角度库该发现但没发现的问题"，防秘书和军师都在同一偏差里谁也发现不了。Explore的触发由秘书在项目复盘时派发（Explore是只读子代理，不能自动触发）。
3. **军师自动触发联网**：军师检测到coverage-gaps.md中"该有但没有"≥2个，自动联网搜索外部方法论补充角度候选。搜索约束：①关键词必须从缺口模式中提取（不能漫无目的搜）②单次触发搜索上限5次（防资源浪费）③搜索范围限定"审视方法""批判性思维""质量控制""风险管理"。搜索结果提炼成角度格式后进入闭环4验证，不直接入库。
4. **记录到coverage-gaps.md**：走岔了检测结果记录在缺覆盖文件里，军师下次整理时读取。

注：军师查（任务级，每次返回）和Explore查（项目级，复盘时）是分级设计——任务级成本低频率高（仅军师内部视角），项目级成本高频率低（加Explore外部视角）。

## 二、整理与维护

### 整理触发
- 角度数≥30个，或
- 相比上次整理增长≥30%，或
- 每50次军师被调用（1个整理周期，见"整理周期定义"小节）
- 三个条件取先到者触发整理
- **紧急触发（v2.14新增）**：任一status文件超过32KB时立即触发紧急清理（只做归档不做分析），不等整理周期

### 整理周期定义（v2.3新增，v2.4修订）
整理周期 = 50次军师被调用。军师被调用 = 秘书派发军师执行任务（提供方案、需求解决、分析事情等）。

- 军师每次被调用时自己把js-dispatch-counter.md的"军师被调用总次数"+1。
- 整理周期计数：军师被调用总次数 - 上次整理时的调用次数 ≥ 50 → 1个整理周期结束，军师自己执行整理。
- "连续N个整理周期" = 连续N×50次军师被调用。
- 如果秘书长时间不派军师（老板暂时不需要方案/分析），整理周期自然拉长——不强制时间，完全由军师调用驱动。
- 周期末军师执行整理时同步执行系统性偏差检查+进化引擎自审，确保周期依赖的规则有计数边界。

### 冷启动检查（v2.13新增，v2.14修订触发条件）
体系首次建立或长时间未运转后恢复时，强制执行一次完整7闭环验证，不等计数到10。

**触发条件**（满足任一即触发）：
1. `js-dispatch-counter.md`中"军师被调用总次数"≤1（体系刚建好首次运转）
2. 距上次冷启动检查超过3个整理周期（150次军师调用）（定期验证流程完整性，不依赖时间维度）
3. 秘书手动指定"冷启动检查"（老板要求验证体系是否正常）

**检查内容**（7个闭环逐个验证）：
1. 闭环1：模拟一次任务派发，验证秘书自审流程能走通
2. 闭环2：检查coverage-gaps.md是否有记录，没有则模拟一次覆盖检查
3. 闭环3：检查angle-proposals.md是否有提案，没有则模拟一次提案
4. 闭环4：验证一个已有角度的证伪流程能走通
5. 闭环5：验证角度入库流程（不实际入库，验证流程步骤完整性）
6. 闭环6：检查angle-feedback.md是否有反馈，没有则标注"待首个真实项目验证"
7. 闭环7：执行一次完整meta-audit（7个健康指标全查）

**结果记录**：写入`status/js-dispatch-counter.md`健康指标检查记录表，dashboard.md"冷启动检查状态"更新为"已执行"。

**关键**：冷启动检查不增加军师调用次数（不是真实任务派发），只验证机制完整性。如果任一闭环走不通，立即记录到issues.md并标注P0。

### 零使用角度判定规则
使用次数=0不直接等于"无用"。先判断"是否有机会被使用"，再决定是否清理：

- 使用次数=0，且入库时间<30天 → 新角度，保留，继续观察
- 使用次数=0，且入库时间>30天 → 触发主动自检：检索过去30天的自审记录，判断是否有该角度的触发场景出现过
  - 有触发场景但没匹配到 → 角度描述或触发场景有误，需要修正
  - 没有触发场景 → 状态改为"待观察"，等待触发
- 使用次数>0，但最近30天内无命中记录 → 同上判断是"场景没出现"还是"匹配有问题"

### 老化检查
- 角度超过90天无命中记录且无修正记录 → 自动标记"待观察"
- 连续2个整理周期仍无命中 → 建议归档（先备份）

### 归档条件（同时满足）
1. 连续3个整理周期处于"待观察"状态
2. 该角度涉及的领域标签在最近1个整理周期内无任何输入出现

### 变更记录归档
- 文件头变更记录超过5条时，最早的记录移到 `memory/.archive/js-cognitive-framework-changelog.md`
- 文件头只保留最近5条变更记录
- 归档文件按时间顺序排列（旧在上、新在下）
- 归档时机：军师每次升版本时检查条数，超过5条即归档最早的

### 版本回滚（v2.10更新，原"修改前备份"+"备份保留策略"合并）
- 备份方式：GitHub统一管理，每日提交（或每次军师执行后提交），不再逐次手动备份
- 回滚方式：`git checkout`回滚到任意历史版本
- changelog类文件作为人类可读变更摘要永久保留
- .archive目录只保留changelog归档和js-archived-angles.md

### 按需联网
联网搜索有两条触发路径（v1.9更新）：

**路径1：自动触发（走岔了检测驱动）**
- 军师读取coverage-gaps.md，检测到"该有但没有"≥2个 → 自动联网搜索
- 关键词必须从缺口模式中提取（不能漫无目的搜）
- 单次触发搜索上限5次（防资源浪费）
- 搜索范围限定"审视方法""批判性思维""质量控制""风险管理"
- 搜索结果提炼成角度格式后进入闭环4验证，不直接入库

**路径2：手动触发（验证时加深理解）**
- 军师在验证新角度时如果理解不够深，联网搜索相关方法论
- 搜索关键词围绕"审视方法""批判性思维""质量控制"等
- 联网结果提炼后追加到角度，标注来源URL

**共同规则**：不联网搜具体业务知识，只搜"怎么思考"的方法论。搜索结果不直接入库，必须提炼成角度格式过5项硬标准验证。

### 角度间冲突解决
- 当两个角度的指导方向冲突时（如"执行优先"vs"授权判断"），按以下优先级裁决：
  1. 安全优先：涉及不可逆操作时，先验证再执行
  2. 上下文优先：具体场景决定哪个角度适用，不硬套
  3. 秘书判断：秘书根据当前情况判断哪个角度优先，并在自审记录中写明理由
- 冲突本身也是学习事件：如果两个角度经常冲突，说明需要修正其中一个或合并
- 结构性冲突（两个角度频繁冲突）由秘书提交修正请求给军师，军师判断合并或修正哪个角度（见 js-cognitive-charter.md 10.2"修正角度描述"职责）

### 系统边界声明
认知框架只做审视判断，不做最终决策。所有审视输出均供秘书和老板参考决策，不替代人做决策。
- 能做：审视判断、提供角度清单、发现覆盖缺口、生成新角度提案、验证角度有效性
- 不能做：替代人做最终决策、自动执行任务状态变更、调用外部API、管理团队成员
- 超出边界时：返回"超出能力边界"提示，不尝试处理

### 死循环防护
- 已打回的缺口记录到"已处理缺口清单"并计数。同一缺口累计被打回<3次时，后续再次遇到同一场景仍可重新生成提案（场景可能已变化，上次打回原因可能不再适用）
- 同一缺口累计被打回≥3次 → 标记"需外部输入"，后续不再自动生成提案，供秘书和老板参考
- 防止角度库在同一个坑里反复空转

### 进化引擎自审（元闭环，v2.0新增）
6条闭环管角度的进化，这一节管6条闭环本身的健康。军师每次整理时与系统性偏差检查同步执行，查7个健康指标：

| 指标 | 查什么 | 预警标准 | 预警后自动做什么 |
|---|---|---|---|
| 闭环活跃度 | 6条闭环（1自审/2覆盖检查/3提案/4验证/5入库/6反馈）是否都有产出记录，分别查js-dispatch-counter.md对应计数器 | 任一闭环连续2个整理周期无活动 | 标记"闭环X停滞"，军师诊断原因（没触发还是触发了没产出），尝试重新触发 |
| 进化速率 | 新增/归档角度比例是否健康 | 新增>5个/周期=太激进；新增=0连续2周期=停滞 | 太激进→收紧验证标准；停滞→触发联网搜外部方法论 |
| 反馈闭合度 | 闭环6结果有没有真正回流到闭环1-5 | 闭环6有反馈但未触发任何处理 | 标记"反馈断裂"，军师重新执行证伪处理流程 |
| 保险有效性 | 4道保险有没有在生效 | 任一保险从未触发且已运行≥3周期 | 标记"保险X可能失效"——从未触发可能是检测机制本身坏了 |
| 标准进化健康度 | 验证标准自进化有没有在改善质量 | 细化后通过率连续上升3次 | 触发秘书审查（不等下次整理） |
| 角度库新陈代谢 | 只进不出=膨胀；只出不进=萎缩 | 连续2周期只进不出或只出不进 | 膨胀→触发整理提纯；萎缩→触发联网补充 |
| 进化方向一致性 | 新角度是否在填补已识别覆盖盲区 | 连续2周期新增角度全在已覆盖领域 | 标记"进化方向偏移"，优先处理覆盖盲区缺口 |

执行要求：
- 军师每次整理时逐项检查7个指标，结果写入 `status/js-dispatch-counter.md`健康指标小节
- **交叉验证（跳过检测，v2.1新增，v2.3修正公式，v2.4改军师自治）**：军师执行meta-audit时自己读取 `status/js-dispatch-counter.md`，自己交叉检查军师被调用总次数 vs 各闭环产出次数。跳过闭环1 = 军师被调用总次数 - 闭环1自审次数（ms-standin-review条目数）。跳过闭环2 = 军师被调用总次数 - 闭环2覆盖检查次数（coverage-gaps更新次数）。跳过闭环5 = 闭环4验证通过次数 - 闭环5入库次数。跳过>0 → js-dispatch-counter.md健康指标小节记录预警 + issues.md追加"闭环跳过"问题 + dashboard标红。公式逻辑：每次军师被调用都应有对应的闭环产出，调用次数-产出次数=跳过次数
- **计数触发meta-audit**：军师被调用总次数 - 上次meta-audit时的调用次数 ≥ 10 → 军师自己执行meta-audit，不需要秘书派发
- **调用即计数**：军师每次被调用时自己+1、自己判断是否到阈值、该做就做。秘书不碰计数器、不参与判断。军师被调用本身就是心跳——如果秘书长时间不派军师，说明老板暂时不需要方案/分析，体系自然安静；秘书该派军师时不派，产出文件无记录，dashboard显示"0次调用"，矛盾就是信号
- 任一指标触发预警，军师自动分析根因并尝试修复
- 机制故障（如闭环断裂）→ 军师尝试重新触发自身负责的环节（闭环2覆盖检查/闭环3提案/闭环4验证/闭环7自审）。闭环1（任务前自审，触发者=秘书派发）、闭环5（入库，触发者=军师手动或项目交付）、闭环6（结果回填，触发者=项目交付）的停滞军师只能标记"需秘书介入"，无法自动修复——这些闭环的触发者是秘书或项目交付，军师无法代替
- 修复失败 → 标记"需秘书介入"，写入js-self-review.md
- **meta自审**：每次整理时（即每50次军师被调用=1个整理周期）秘书检查js-dispatch-counter.md健康指标小节是否有更新。如果文件超过1个整理周期（50次军师调用）未更新 → 说明meta-audit本身停了 → 秘书手动触发军师执行一次自审
- **关键**：这是"审查审查者"的元闭环。没有这条，如果6条闭环悄悄停转，体系里没有任何东西能发现
- **引用图检查（v2.13新增）**：meta-audit时额外执行一次引用图检查——grep所有规则文件中的交叉引用（"详见xxx.md"、"见xxx"），构建引用关系图，检测循环引用（A→B→A但都不含正文）。发现循环引用标P0，记录到issues.md。js-end.sh的verify_refs函数提供基础检查，meta-audit时军师做深度人工审查。

## 三、执行流程与保证

### 军师执行自回顾（v2.4新增，v2.14修订触发门槛）
军师每次执行完任务后，自己判断这次值不值得写详细自回顾。

**必须写详细自回顾的情况**（以下任一即触发）：
1. DET自检有不通过项
2. 修改了角度库内容（新角度入库/角度修正/角度归档）
3. 被秘书或老板指出问题
4. 首次执行某类任务（之前没做过的类型）

**不触发详细自回顾时**：只填自回顾记录表格行（1行），不写详细自回顾段落。这样常规执行的自回顾开销从37-79行降到1行。

**回顾不是重做**，是回头看自己执行过程中有什么问题。

**自回顾内容**：
1. **做了什么**：这次执行的任务简述
2. **遇到的问题**：执行过程中碰到什么问题（流程不顺/规则矛盾/工具限制/自己判断失误等）
3. **已改进**：本次直接改了什么（限角度库内容，走闭环4验证+闭环5入库流程）
4. **流程优化提案**：发现但不能直接改的（规则/流程/职责问题），写提案到issues.md，秘书审查后决定改不改
5. **历史重复**：翻js-self-review.md历史记录，看这个问题是第几次出现。>1次说明根因未解决，≥3次必须在下次自回顾中给出根因分析

**自改进边界**：
- 军师直接改：只限角度库内容（新角度入库/角度修正/角度归档）
- 军师不能直接改：宪法规则、执行流程、职责定义、角色模板——发现问题写提案到issues.md
- 理由：规则级改动无人监督有风险，必须秘书审查

**报告输出**：写入 `status/js-self-review.md`，格式见该文件

**与闭环7的区别**：
- 闭环7（meta-audit）查体系健不健康（系统级，每10次调用）
- 自回顾查这次做得好不好（任务级，每次执行完）
- 两者互补，不替代

### 短期记忆合并策略（v2.12新增）
js-cognitive.md达到20条上限时，不直接删最旧的，先执行合并：

1. **识别相似**：同一任务多次执行/同一问题反复出现/同一规则多次调整的记忆条目
2. **合并规则**：保留最新条目编号，内容融合（最新执行细节+旧条目历史背景），标注"[已合并X条]"
3. **冲突处理**：如有事实冲突（旧说A对、新说A错），保留所有描述并标"需人工审查"
4. **合并后检查**：合并后仍超20条→删最旧的。被删条目检查有无反复出现的模式，有则融合进js-cognitive-longterm.md

### status文件清理机制（v2.4新增）
所有status文件只会越攒越多，没有出口会越来越长。军师每次整理时（每50次调用）对所有status文件执行清理：

**适用文件**：js-self-review.md / angle-feedback.md / ms-standin-review.md / coverage-gaps.md / issues.md / js-dispatch-counter.md（日志部分+健康指标小节）/ gray-areas.md / angle-proposals.md / standard-changes.md

**清理动作**：
1. **合并重复**：同一问题/记录多次出现→合并成一条，标注出现次数
2. **标记已解决**：问题已修复→标记"已解决"+日期，不再计入活跃问题
3. **归档旧记录**：超过最近20条或超过50KB的旧记录移到 `.archive/{filename}-archive.md`（双重阈值，取先到者）
4. **重复问题升级**（仅js-self-review.md）：同一问题出现≥3次且未解决→升级到issues.md标"高优先级"
5. **归档文件压缩（v2.14新增）**：归档文件自身超50KB时，将最早的条目压缩为一行摘要（保留序号+日期+核心发现一句话），原文保留在摘要下方的折叠区。归档文件分为"摘要区"（最早条目的一行摘要）和"全文区"（最近条目的完整记录），单文件内完成，不搞二级目录
6. **新增文件同步（v2.14新增）**：新增status文件时，必须同步加入本"适用文件"列表。遗漏=清理不完整

**清理结果**：写入js-self-review.md的整理记录中，说明清理了哪些文件、合并/标记/归档了多少条

军师执行流程脚本化（ANGLE-023）的配套管理规则。

**脚本位置**：`/workspace/.team/scripts/js-start.sh`（开工脚本）和 `/workspace/.team/scripts/js-end.sh`（收工脚本）

**版本管理**：

- 脚本修改时递增版本号
- 脚本是纯bash无外部依赖，保持这一约束

**DET分层读取规则（v2.13融合更新）**：

**DET效果追踪（v2.13新增，v2.14补回填规则，v2.15修订降级机制）**：
- 每条DET记录"拦截次数"——执行前读到了这条DET并发现了问题（哪怕只是"我注意到这个风险"），拦截次数+1
- **回填规则（v2.14新增）**：每次自回顾的DET自检中标记为"不通过"或"通过且发现问题"的检测项，必须在检测项清单中对应条目的拦截次数+1。遗漏视为自回顾不合格，下次meta-audit时军师补回填
- 拦截次数=0且军师被调用总次数≥50 → 标"待评估"，军师判断该DET是否还有存在价值
- 连续2个整理周期拦截次数=0 → 标"待验证"，军师回顾该DET的触发场景是否曾出现。场景曾出现但DET未拦截→降级为"参考DET"（保留在清单但不进入active读取列表，只在精确匹配场景时手动查阅）；场景未出现→保留，继续等待。**降级不归档**——规则有认知价值不应删除
- 拦截次数≥3 → 按现有规则提案为新角度（走正常角度验证流程入库）
- 拦截次数记录在`status/js-self-review.md`检测项清单的"拦截次数"列

**DET融合机制（v2.15新增，替代原"规则剪枝"）**：
- 整理周期时检查DET清单中是否存在"本质是XX变体"或"已被XX增强覆盖"的条目。有→执行融合
- 判断标准：①检测方法已被另一条增强版完全覆盖→被覆盖方融入覆盖方；②互相标注"本质是对方变体"→合为一条；③已弃用DET底层原则仍有效→融入对应角度规则条目
- **覆盖度评估**：逐条比对被吸收方的检测方法+通过标准的每个要点，在合并主体中是否有对应表述。有对应才算覆盖，无对应的要点必须补入合并主体后才能融合
- **追溯机制**：被吸收DET的完整条目移到归档区按原编号可检索；合并主体的"具体检查场景"中保留原编号+一句话关键检测要点
- **即时检查**：每次新增DET时，立即检查是否与现有DET有归属关系。如果有，直接融合，不等整理周期

**自检规则**：
- `js-start.sh --check` 自检验证关键文件路径有效
- 自检频率：每10次调用执行一次--check（非每50次）
- 自检不通过时输出具体错误信息，军师需手动修复

**脚本维护触发条件**（只有以下3种结构性变更才需要改脚本）：
1. `.team`目录结构变化（文件改名/移动）
2. grep匹配模式失效（管理规则节标题改名）
3. 军师执行流程增加新的固定必读步骤
- 正常使用下接近零维护。新增DET检测项不需要改脚本（grep动态发现）

### 联动修改范围规则（v2.9新增）
角度定义变更时，需要修改的文件分两类：

**A类-真正联动（需思考）**：
- js-cognitive-framework.md（规则本身）—— 必须改，这是改的对象
- changelog.md归档 —— 机械操作（超5条归档最早的），不需要思考

**B类-固定执行日志（不管改什么每次都得写）**：
- js-cognitive.md（一句话记忆）—— 每次执行必写，不算联动成本
- js-self-review.md（自回顾）—— 每次执行必写，不算联动成本
- js-dispatch-counter.md（计数器+1）—— 每次执行必写，不算联动成本

**不联动**：
- js-cognitive-longterm.md —— 记的是历史经验模式，不是当前规则镜像。角度优化（如ANGLE-020从"每处读回"改为"最后统一验证"）不改变核心经验（"不能并行会覆盖"），长期记忆不跟随规则优化联动更新。只有核心经验本身被证伪时才更新长期记忆。

**效果**：角度定义变更的真正联动成本 = 1个需要思考的文件（js-cognitive-framework.md）+ 1个机械操作（changelog归档）。

### 执行保证（v2.7，原宪法11.9迁移）

通过三层机制把"应该"变成"必须"。军师自计数/交叉验证/跳过检测的完整规则详见"进化引擎自审"小节，此处只保留三层关系总览。

**秘书职责边界**：秘书只负责调度和翻译。计数、触发判断、执行动作都由军师自己做。

**三层关系**：

| 层 | 强制什么 | 强制力来源 | 什么时候生效 |
|---|---|---|---|
| 闭环绑定 | 闭环1-6每次军师调用有产出记录 | 产出文件=证据+军师交叉验证 | 每次军师被调用时 |
| 军师自计数自触发 | 闭环7定期执行+跳过检测 | 军师自己+1到10次自己做+交叉验证 | 每10次军师被调用 |
| 看板可见 | 老板一眼看到引擎状态+跳过差值 | 老板的注意力 | 随时 |

**无法100%保证的部分**（诚实声明）：
- 闭环绑定依赖秘书执行闭环1-2——如果跳过，军师交叉验证会发现差值（调用次数≠产出次数），dashboard标红
- 军师自计数依赖军师被调用——如果秘书该派军师时不派，军师没机会+1和触发，dashboard显示"0次调用"但老板有实质需求，矛盾本身是信号
- **最终兜底**：老板。看一眼dashboard的计数差值和健康判定颜色，就知道引擎有没有在转、有没有跳过

## 四、提案与质量保证

### 提案前置检查（v2.15新增）

> 来源：DET融合方案3轮讨论复盘（2026-08-15）。根因：提案从"分析"直接跳到"提交"，缺少"方案质量验证"环节。
> 原则：每次出现问题转化为预防机制，不再重复发生。第一次出现的新错误类型靠人发现，之后靠机制拦截。

**触发条件——什么算"结构性变更"**：
1. 新增/修改/删除/融合DET
2. 新增/修改/归档角度
3. 新增/修改管理规则
4. 修改角度库或DET的触发条件/通过标准/分层标注
5. 修改js-start.sh/js-end.sh脚本逻辑

非结构性变更（修错别字、格式调整、数字微调不改语义）不触发。

**强制层（每次提案必做，约15分钟）**：

1. **交叉引用扫描**：按变更类型执行grep，列出影响面清单
   - 改DET→扫描ANGLE规则中的DET引用+js-start.sh变量+DET分层标注表
   - 改ANGLE→扫描其他ANGLE引用+DET引用+宪法引用
   - 改管理规则→扫描脚本依赖的grep模式+其他规则引用
   - 改脚本→扫描规则中引用的脚本行为+变量名
   - 兜底：不在上述类型中→按变更对象名称grep全.team目录（排除.archive）
2. **数字自验**：逐项验证方案中所有数字/计数。
   - **自动化验证优先**（能机器数的不要手数——军师有DET-002形式合规前科3次，手数不可靠）：
     - DET数量→`awk -F'|' 'NF>=7 && $2 ~ /DET-/' js-self-review.md | wc -l`（只匹配检测项清单表，不匹配分层标注表和自回顾记录中的DET行）
     - 角度数量→`grep -c '^### ANGLE-' js-cognitive-framework.md`
     - 规则数量→`grep -c '^### ' js-cognitive-rules.md`（数节标题）
     - 文件大小→`wc -c < 文件路径`
     - 引用数量→`grep -c 'DET-0' 文件路径`（注意DET-012过宽风险，需确认匹配范围）
   - **无法自动化的数字**（如"预计节省X分钟"）：人工估算+标注"估算值非实测"
   - **二次验证**：自动化验证不需要二次验证（机器不会数错）；人工验证必须二次独立验证（不看第一遍结果重新数一遍，两次一致才算通过）
3. **结论一致性自验**：方案中每个假设性结论（如"D组保持独立"）与基于该结论的计算（如"融合后8条"）必须用同一假设。通读方案找出所有"假设性结论"，验证后续计算是否基于同一假设

**触发层（条件满足时做）**：

4. **价值维度考虑**（破坏性方案——删除/归档/移除操作时触发）：被删除/修改的东西有没有认知价值？能保留价值同时解决问题吗？至少考虑2个方案（1个破坏性+1个保守性），说明为什么选当前方案
5. **跨提案协同检查**（**v2.17改为每次必做**）：每次提案至少快速检查一次路径/格式/INDEX一致性。若issues.md无其他待审批提案且本次只提1个方案→快速检查（确认路径格式与现有体系一致即可）；若有多方案或issues.md有待审批提案→完整检查重叠/可合并/路径/格式/INDEX一致性
6. **角度库审视**（结构性变更时触发）：用至少2个角度审视方案。推荐ANGLE-017反面论证（如果方案错了会怎样？——含框架挑战，自查和审查他人时都做）+ANGLE-005找盲区（还有哪些没考虑到？方案是否回答了该回答的所有问题？——含方案完整性检查+语义一致性检查：新规则与现有DET/角度/规则在含义上是否重叠或矛盾？重叠→说明分工或合并，矛盾→修正）+ANGLE-019可逆性（能回滚吗？）
7. **覆盖度评估**（融合/合并类方案触发）：逐条比对被吸收方的检测方法+通过标准的每个要点，在合并主体中是否有对应表述。有对应才算覆盖，无对应的要点必须补入合并主体后才能提交。引用DET融合机制的覆盖度评估标准

**军师自己提案时**：执行强制层3项 + 所有条件满足的触发层项。军师有DET-002形式合规前科3次（序号007/008/009），审查能力≠提案时的自我审查能力——自己提案时尤其不能省略Check 2命令行验证（复盘进化点1，2026-08-15）
**审查他人提案时**：执行强制层3项 + 所有条件满足的触发层项（4/5/6/7中条件满足的都做，不是限死某几项）

**复盘转化（方案被退回时触发）**：
- 记录问题类型（问题模式，不是具体问题——如"未考虑替代方案""数字未自验"）
- 检查现有规则是否已覆盖该模式（翻js-self-review.md复盘转化小节的历史记录）
- 未覆盖→提案新增检查项（走简化版前置检查：只做强制层3项，避免递归无界）
- 已覆盖但仍发生→增强现有检查项执行力度（如从"建议"改为"强制"）
- 记录到js-self-review.md"复盘转化"小节

**执行证据记录**：每次前置检查后，在提案文档末尾追加7行表格（Check 1-7各一行：检查项|是否执行|结果）。格式见js-self-review.md。不做记录视为未执行。

**与现有机制的关系**（防混淆，防跳过旧DET）：
- Check 2 vs DET-002：Check 2数对没，DET-002算没算+算的对不对。互补都做
- Check 3 vs DET-007：Check 3是DET-007子集（只查结论-计算矛盾）。互补都做
- Check 6 ANGLE-017 vs 验证标准第4项：验证标准第4项是ANGLE-017在新角度入库场景的特化版
- Check 6语义一致性 vs 联动修改规则：联动查字面依赖，Check 6查语义依赖。互补不冲突
- 复盘转化 vs ANGLE-022：复盘转化是ANGLE-022在提案流程层的应用（转化为检查项而非DET）

**诚实声明**：前置检查降低错误概率但不消除——第3轮证明军师做了数字自验但数字是错的。检查过的方案仍被退回→触发复盘转化。最终兜底是老板抽查。

**数字可靠性分层**（v2.16新增）：
- 高：自动化验证（awk/wc/grep计数，经实测验证匹配范围正确）——机器不受认知盲区影响
- 中：人工二次独立验证——同一人两遍可能犯同样错误（相关性错误），但比单遍好
- 低：人工单次验证——有3次形式合规实质失效前科
- 估算值（如"预计节省X分钟"）：标注"估算值非实测"，不与实测值混用

### 缓存使用规则（v2.16新增，硬障碍3配套）

1. **读缓存前必须验hash**：任何缓存文件读取前，先比较source_hash与当前源文件md5。不一致→回退读源文件+输出警告
2. **hash校验由脚本层执行**：js-start.sh在加载时自动校验缓存hash，校验通过的缓存才展示给军师，校验失败的不展示+回退读源文件。军师不直接读.cache文件——军师拿到的永远是已校验内容
3. **缓存过期不静默使用**：这是DET-014"空返回静默"在缓存场景的变体。静默使用过期缓存=把错误数据当正确数据
4. **缓存不存在不报错**：缓存是加速手段不是必需品。缓存不存在时直接读源文件
5. **缓存生成在收工时**：js-end.sh收工时（git commit后）生成/更新缓存，确保缓存反映最新状态
6. **缓存不入git**：.cache目录在.gitignore中排除，缓存可重新生成不需要版本追踪

### 机器执行优先原则（v2.17新增，硬障碍复盘进化点3）

> 来源：三个硬障碍复盘（2026-08-15）。军师能识别"自己不可靠"的领域（DET-002前科3次），但识别≠执行——自觉校验不可靠。
> 原则：凡是有机器可执行路径的保障，优先脚本执行，不靠军师自觉。

1. **识别机器可执行路径**：提保障方案时，先问"这个保障能不能由脚本/工具自动执行？"能→脚本执行；不能→人工执行但标注"依赖军师自觉（可靠性低）"
2. **脚本执行优先级高于人工自觉**：同一保障既有脚本路径又有人工路径时，选脚本路径。例：缓存hash校验由js-start.sh脚本层执行（不依赖军师自觉Read前验hash）
3. **不靠自觉的领域**：军师有DET-002形式合规前科3次，涉及数字验证/格式检查/路径一致性等可机器化的检查，不靠军师"自觉记得查"
4. **无法脚本化的保障**：标注"依赖人工判断"，承认可靠性低于脚本执行。不假装人工检查等同于脚本检查

### 修改完整性验证（v2.18新增，P2升级——从建议到强制）

> 来源：秘书二次分析反馈遗漏1（2026-08-15）。军师修了cache-intelligence-review.md第233行`status/.cache/`路径但漏了第256行同路径，没用grep全文件验证。DET-002第5次形式合规实质失效。
> 原则：修改类待办完成后必须用grep全文件验证修改完整性，不靠军师自觉"我觉得改完了"。这是"机器执行优先原则"在修改验证场景的具体应用。

1. **修改类待办定义**：涉及查找并替换/修正特定模式的操作（如路径修正/变量改名/格式统一/字符串替换）
2. **强制验证**：修改完成后，用grep搜索原模式（被修改的模式），返回0匹配才算修改完整。返回>0匹配说明还有遗漏
3. **验证命令示例**：`grep -n '旧模式' 文件路径`——返回0行=修改完整，返回>0行=有遗漏
4. **不适用场景**：语义性修改（非字符串替换）、新增内容（非查找替换）、格式微调（不影响内容）
5. **与Check 2的关系**：Check 2管"数字对不对"（数一遍），本规则管"改全了没"（grep验证修改完整性）。互补不冲突
6. **局限性**（ANGLE-005找盲区）：grep只验证字符串模式完整性，不验证语义正确性。语义性修改仍需人工通读检查

### 文件修改后同步更新INDEX.md（v2.18新增，遗漏4进化）

> 来源：秘书二次分析反馈遗漏4（2026-08-15）。军师修改js-cognitive-rules.md后文件为45KB，但INDEX.md标注44KB。军师称"INDEX.md不在修改权限内"，但INDEX.md文件头标注"维护者：军师（每次整理时更新大小）"。
> 原则：INDEX.md是军师负责维护的文件。每次修改memory/或status/下的文件后，INDEX.md中对应的大小和描述都应同步更新。

1. **修改后同步检查**：每次修改memory/或status/下的文件后，检查INDEX.md中对应条目的大小和用途描述是否需要更新
2. **大小更新标准**：文件大小变化超过1KB时更新INDEX.md中的大小标注（四舍五入到KB）
3. **描述更新标准**：文件内容有实质性变化（新增/删除小节、功能变更）时更新用途描述
4. **底部摘要同步**：INDEX.md底部"当前超阈值文件"摘要行也必须同步更新（不只改表格条目——秘书在修复遗漏4时只改了表格条目45KB但漏了底部摘要仍写44KB，犯了同样的"局部修正不完整"错误）
5. **归档后更新**：对js-self-review.md等执行归档后，INDEX.md中对应大小必须更新为归档后的大小
6. **全局文件体积检查**（遗漏3进化，v2.18新增）：修改任何文件后，不只检查被修改文件的体积，必须全局检查所有管理文件的体积是否超阈值。具体操作：`wc -c memory/*.md status/js-self-review.md status/.archive/*.md`一次性输出所有管理文件大小，对照INDEX.md底部阈值摘要检查。根因：军师序号015只检查了被修改的js-cognitive-rules.md（45KB<48KB）但漏检js-self-review.md（41.5KB>32KB），"局部正确但全局遗漏"
