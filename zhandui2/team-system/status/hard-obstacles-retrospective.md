### 必改2：.cache 路径三方不一致

**军师指出**：硬障碍1(.cache/) vs 硬障碍3(.cache/) vs cache-review(status/.cache/) 三处路径冲突。

**落地情况**：已统一为 `.team/.cache/`。
- `.gitignore` 写 `.cache/`（排除根级缓存目录）

### 必改3：grep 模式有过宽风险（DET-012变体）

**军师指出**：方案给的自动化验证示例模式会匹配多张表，高估约1倍。

**落地情况**：已采纳军师建议。DET-002的自动化对照检测方法中，示例命令使用 `awk -F'|' 'NF>=7 && $2 ~ /DET-/'`（复用js-start.sh已验证的awk字段数过滤模式），而非简单 `grep -c '^| DET-'`。该模式通过字段数(NF>=7)区分定义表(8字段)和自检表(5字段)，已在js-start.sh的display_det函数中实测有效。

### 必改4：可靠性百分数是估算值（递归犯DET-002）

**军师指出**：95%/70-80%/60%三个百分数无计算过程，恰恰是DET-002的再次重演。

**落地情况**：已采纳军师推荐方案——去掉具体百分数，改用定性分级：
- 高：自动化验证（awk/wc/grep计数，经实测验证匹配范围正确）
- 中：人工二次独立验证
- 低：人工单次验证
- 估算值（如"预计节省X分钟"）：标注"估算值非实测"

并在分级旁标注"本分级为定性判断，非实测百分数"。

### 必改5：缓存hash校验执行者不明确（最大遗漏）

**军师指出**：方案把"脚本校验"和"军师自觉校验"混为一谈，军师有DET-002前科，自觉校验不可靠。

**落地情况**：已采纳军师推荐的方案A——脚本层执行hash校验。具体实现：
1. **js-start.sh开工流程**（第368-394行）：读取缓存前先由脚本算md5比对，校验通过才展示缓存内容给军师，校验失败则输出"缓存过期，回退读源文件"并直接cat源文件。军师拿到的永远是已校验内容。
2. **js-start.sh --check**（第187-216行）：遍历所有缓存文件，逐个校验source_hash与当前源文件md5。校验通过输出[OK]，过期输出[WARN]，源文件不存在输出[FAIL]。
3. **js-cognitive-rules.md缓存使用规则**第2条明确："hash校验由脚本层执行，军师不直接读.cache文件——军师拿到的永远是已校验内容"。

**关键设计决策**：军师不直接Read .cache文件。缓存只通过js-start.sh脚本输出访问。这从根本上消除了"军师自觉校验"的可靠性风险。

### 必改6：跨方案路径/格式/INDEX对齐检查

**军师指出**：三个方案各自没看到对方，路径/格式/INDEX未跨方案对齐。

## 三、执行过程关键决策记录

### 决策1：git提交时机——放最后（verify_refs之后）

**军师建议**：方案说"计数器更新后、引用检查前"，但逻辑上"所有收工写操作完成后提交"更清晰。

**落地情况**：已采纳。js-end.sh主流程顺序为：
1. increment_counter（计数器+1，写操作）
2. verify_refs（引用一致性检查，只读不写）
3. git_commit_changes（git自动提交，放最后）
4. generate_cache（缓存生成，git提交后执行）

### 决策2：缓存元数据精简为source_path + source_hash

**军师建议**：若采用方案A（脚本每次开工校验），则.cache文件不需要存generated_at/generated_by/expires等字段。

**落地情况**：已采纳。缓存文件元数据头精简为：
```
## Cache Metadata
source_file: js-cognitive-framework.md
source_path: /workspace/.team/memory/js-cognitive-framework.md
source_hash: <md5值>

## Cache Content
<缓存内容>
```
只存source_path + source_hash两项核心元数据。source_file是人可读的文件名（非逻辑必需）。

### 决策3：--check缓存校验空目录处理

**军师提醒**：.cache不存在时遍历应输出"无缓存文件，正常"而非报错。

**落地情况**：已处理。js-start.sh --check 第189行：
```bash
if [ -d "$CACHE_DIR" ] && [ -n "$(ls -A "$CACHE_DIR" 2>/dev/null)" ]; then
    # 遍历校验
else
    echo "  [INFO] 缓存目录不存在或为空（尚未生成缓存，属正常）"
fi
```
空目录/不存在目录输出[INFO]而非[FAIL]，符合"缓存是加速手段不是必需品"的哲学。

### 5.2 军师自身的进化点

**进化点1：审查他人方案时能精准发现问题，但自己提方案时同样会犯**

军师在审查硬障碍2方案时，精准发现"可靠性百分数是估算值"——这恰恰是DET-002要防的错误。但军师自己在cache-intelligence-review.md中提缓存收益评估时，也用了未经实测的估算数字（被军师自己在后续审查中纠正）。

这说明：**审查能力和提案能力是两种能力**。军师的审查能力已达到可靠水平（6/6命中），但提案时的自我审查仍不可靠。这验证了军师在proposal-review-military-advisor-final.md第八节的自评——"查别人的数字错误能抓到，自己的数字错误抓不到"。

**进化建议**：军师提案时，应假设"自己提的方案会有DET-002类错误"，强制走提案前置检查的Check 2（数字自验），且数字必须用命令行验证（不只手数）。

**进化点2：跨方案视角是军师的弱项**

三个硬障碍方案各自独立提出，路径/格式不一致。军师在审查时发现了这个问题（共性问题2），但军师自己在提cache-intelligence-review.md时也没检查与已有方案的路径一致性。

这说明：**军师在单方案深度审查上能力强，但在跨方案协同检查上需要Check 5的强制触发**。

**进化建议**：军师每次提案时，Check 5（跨提案协同检查）应从"条件触发"改为"强制触发"——至少检查一次路径/格式/INDEX一致性。

**进化点3：脚本层执行 vs 军师自觉执行的可靠性差异**

军师在审查硬障碍3时发现了最关键的遗漏——"脚本校验"和"军师自觉校验"的可靠性差异。这个发现直接导致了方案A（脚本层执行hash校验）的采纳，从根本上消除了过期缓存静默使用的风险。

这说明：**军师能识别"自己不可靠"的领域，并主动设计不依赖自己自觉的机制**。这是一种高阶的元认知能力。

**进化建议**：将"凡是有机器可执行路径的保障，优先脚本执行，不靠军师自觉"作为一条管理规则写入js-cognitive-rules.md。这已是军师在hard-obstacles-fix-review.md第五节提出的"统一原则建议"，建议正式入库。
