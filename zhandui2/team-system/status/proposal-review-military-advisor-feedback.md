# 军师自审：提案前置检查方案反馈

> 日期：2026-08-15
> 背景：老板要求军师审视"提案前置检查"方案，补充遗漏，建立"发现问题→自我改进→不重复发生"机制
> 原则：从不同角度发现问题，每次出现问题都转化为预防机制，不再重复

---

## 一、军师对4项前置检查的逐项评估

### 检查1：替代方案考虑 —— 评价：方向对，但不够

**问题**：只要求"1个破坏性+1个保守性"，但实际上第1轮的根因不是"没考虑2个方案"，而是**没有从"价值保留"角度思考**。我提"删除"时，脑子里根本没想过"规则有认知价值"这个维度。

**补充建议**：替代方案考虑应增加一个**价值维度检查**——"这个方案删除/修改的东西，有没有认知价值？如果有，能不能保留价值的同时解决问题？"这不是"想2个方案"能覆盖的，这是一个思考角度。

**与现有角度的关系**：ANGLE-018"成本效益"问"有没有更简单的方式"，ANGLE-019"可逆性"问"能回滚吗"。但**没有角度问"被删除的东西有没有价值"**。这是一个新的思考维度。

### 检查2：交叉引用扫描 —— 评价：正确，但执行规则要细化

**问题**："grep所有引用了待改项的文件"说起来简单，但第2轮我就是没做。原因是：我改DET时脑子里想的是"DET清单在self-review.md"，没有想到ANGLE-024也引用了DET编号。

**补充建议**：交叉引用扫描不能只靠"想起来去grep"，应该有**触发清单**：
- 改DET → 扫描ANGLE规则中的DET引用 + js-start.sh变量 + DET分层标注表
- 改ANGLE规则 → 扫描其他ANGLE是否引用本角度 + DET是否引用本角度 + 宪法是否引用
- 改管理规则 → 扫描脚本是否依赖该规则的模式 + 其他规则是否引用本规则

这个触发清单应作为规则附件，每次提案时对照执行，不靠记忆。

### 检查3：跨提案协同检查 —— 评价：正确，但缺少载体

**问题**：第3轮军师漏了DET融合和ANGLE-024简化的协同，根因是**没有地方记录"当前有哪些待审批提案"**。提案散在对话里，审完一个看下一个，没有全局视图。

**补充建议**：在`issues.md`增加"待审批提案"区域。军师每次提案时先看这个区域，提案入区，审批后出区。这样跨提案协同检查有据可查。但要注意：这个区域不能太重，否则成了项目管理工具。简单一行一条即可：`| 提案名 | 涉及文件 | 状态 |`

### 检查4：数字自验 —— 评价：正确，但应该扩展

**问题**：第2轮和第3轮都犯了数字错误，但根因不只是"没数一遍"。第3轮军师的错误是**D组建议独立但按融合算数量**——这不是数错了，是**结论和计算用了不同假设**。

**补充建议**：数字自验应扩展为**结论一致性自验**——方案中每个结论（如"D组保持独立"）和基于该结论的计算（如"融合后7条"）必须用同一假设。具体操作：提交前通读方案，找出所有"假设性结论"，验证后续计算是否基于同一假设。

## 二、军师发现的4项方案遗漏

### 遗漏1：审查者自身也需前置检查

方案第4条说"审查他人提案时同样执行这4项检查"——方向对，但**不够**。审查者有自己特有的盲区：

- **确认偏差**：审查者倾向于确认提案者的框架，而不是挑战框架本身。军师第2轮审查时接受了"D组应该融合"的框架，只是在细节上找问题，没有质疑"D组该不该融合"本身
- **结论自验**：审查者给出审查结论后，没有规则要求验证自己的结论是否自洽。军师说"D组保持独立"但又算"7条"，就是结论没自验

**补充建议**：审查者额外增加一项检查——**框架挑战**：审查时必须回答"如果提案者的整个框架是错的，会怎样？"这不是找方案内的问题，是质疑方案的前提。

### 遗漏2：缺少"复盘转化"机制

老板说"每次出现问题都不要再重复发生"。4项前置检查解决了"提案前检查"，但**没有解决"问题发生后如何转化为预防机制"**。

这次来回讨论3轮，每轮发现的问题类型不同。如果没有系统化的转化流程，下次出现新类型的问题，还是得靠老板来发现。

**补充建议**：增加"复盘转化规则"——每次方案被退回或审查发现问题后，军师必须：
1. 记录问题类型（不是具体问题，是问题模式——如"未考虑替代方案""数字未自验"）
2. 检查现有规则是否已覆盖该问题模式
3. 如未覆盖→提案新增检查项（走提案前置检查流程，递归）
4. 如已覆盖但仍然发生→增强现有检查项的执行力度（如从"建议执行"改为"强制执行"）

**落地形式**：在`js-self-review.md`的整理记录中增加"复盘转化"小节，每次方案被退回时填写。

### 遗漏3：缺少"不同角度审视"的强制触发

老板说"从不同的角度"。现有角度库有24个角度，但**没有规则要求军师在提案前用哪些角度审视**。第1轮我提"删除"时，如果用了ANGLE-019"可逆性"（删了能恢复吗）或ANGLE-018"成本效益"（有没有更简单的方式），可能就不会直接提删除。

**补充建议**：提案前置检查增加第5项——**角度库强制审视**：提案前必须用至少2个角度审视方案。具体哪些角度？
- ANGLE-017"反面论证"：如果这个方案错了会怎样？
- ANGLE-019"可逆性"：这个方案能回滚吗？
- ANGLE-018"成本效益"：有没有更简单的方式？
- 根据方案类型选择其他相关角度

### 遗漏4：前置检查自身的"开销控制"

4项（+我补充的3项=7项）前置检查，每次提案都做，会不会太重？

**补充建议**：前置检查分两层：
- **强制层**（每次必做）：交叉引用扫描 + 数字自验 + 结论一致性自验。这3项是机械操作，开销小。
- **触发层**（特定条件触发）：替代方案考虑（破坏性方案才触发）+ 跨提案协同（有其他待审批提案才触发）+ 角度库审视（结构性变更才触发）+ 框架挑战（审查时才触发）+ 复盘转化（方案被退回才触发）

这样常规提案只做3项机械检查（5分钟内完成），重大提案才做全部7项。

## 三、军师总结：修订后的完整方案

```
### 提案前置检查（v2.15新增）

军师提交任何结构性变更方案前，必须完成以下检查。

**强制层（每次必做）**：
1. 交叉引用扫描：按"变更类型→扫描清单"执行grep，列出影响面
   - 改DET→扫描ANGLE规则DET引用+js-start.sh变量+分层标注表
   - 改ANGLE→扫描其他ANGLE引用+DET引用+宪法引用
   - 改规则→扫描脚本依赖模式+其他规则引用
2. 数字自验：逐项验证方案中所有数字/计数
3. 结论一致性自验：方案中每个假设性结论与基于该结论的计算必须用同一假设

**触发层（条件触发）**：
4. 价值维度考虑（破坏性方案触发）：被删除/修改的东西有没有认知价值？能保留价值同时解决问题吗？
5. 跨提案协同检查（有其他待审批提案触发）：检查issues.md待审批提案区域是否有重叠或可合并执行
6. 角度库强制审视（结构性变更触发）：用至少2个角度审视方案（推荐ANGLE-017反面论证+ANGLE-019可逆性）
7. 框架挑战（审查他人提案触发）：必须回答"如果提案者的整个框架是错的，会怎样？"

**复盘转化（方案被退回触发）**：
- 记录问题类型（问题模式，不是具体问题）
- 检查现有规则是否已覆盖该模式
- 未覆盖→提案新增检查项；已覆盖但仍发生→增强执行力度
- 记录到js-self-review.md"复盘转化"小节

**审查他人提案时**：执行强制层3项 + 触发层第7项（框架挑战）
```

## 四、军师自评

**能自己改进吗？能。** 

这7项检查全是军师自己能执行的：grep是命令、数数字是数数、查issues.md是读文件、用角度审视是思考过程、框架挑战是思考过程、复盘转化是记录。不需要外部输入，不需要老板参与。

**会不会增加太多开销？不会。** 强制层3项是机械操作，5分钟内完成。触发层只在特定条件下才做。复盘转化只在方案被退回时才做。

**能不能保证不再重复发生？基本能。** 每次出现新问题类型，复盘转化机制会把它变成新的检查项。但有一个诚实声明：如果军师自己执行前置检查时也犯了"数字算错"的错误（如第3轮），前置检查本身也可能失效。这是"谁来监督监督者"的经典问题。建议老板偶尔抽查前置检查的执行质量，作为外部校验。
