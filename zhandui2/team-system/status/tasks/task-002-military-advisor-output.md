## 一、角度库审视

用 ANGLE-005（找盲区）、ANGLE-008（防糊弄）、ANGLE-017（反面论证）、ANGLE-022（机器执行优先）审视本任务。

### ANGLE-005 找盲区

秘书提供的3个开源项目覆盖了追问机制的核心思路，但有4个盲区：

**盲区1：场景不限于软件开发**
prd-maker 的8要素和 interview-agent 的10阶段全部为软件开发导向（Problem Space / Data Architecture / Integration Boundaries / Security & Auth 等）。老板明确说"我们的场景不限于软件开发（也可能是调研/分析/优化等任务）"。直接照搬任何一个项目的维度清单，在非软件任务上会问一堆不相关的问题，或漏掉关键维度。

**解法**：设计通用核心维度（适用于任何任务类型）+ 场景附加维度（按任务类型追加）。军师收到指令时先判场景，再选维度。

**盲区2："已覆盖"判断标准缺失**
prd-maker 说"已答的维度跳过"，但没有定义"什么算已答"。如果军师判断"老板说了做什么"就认为"范围与边界已覆盖"，但老板其实没说不做什么——这个判断就是错的。没有明确的覆盖标准，"已答跳过"机制会变成"军师觉得答了就跳过"的主观猜测。

**解法**：每个维度必须定义"已覆盖"的硬标准（具体到什么信息出现了才算覆盖），不能靠军师感觉。

**盲区3：追问结果去向不明**
3个项目都是自包含系统（追问完直接生成PRD）。我们的体系里追问执行者是秘书，但需求文档由PM写。追问结果怎么交给PM？放在哪？PM怎么读？任务文件没有提到这个交接点。

**解法**：追问结果写入 status/probing-result-{project}.md，PM派发时prompt中指定读取该文件。

**盲区4：追问可能改变老板意图**
追问时如果给的选择有引导性（比如只给A/B两个选项，但老板的真实想法是C），追问本身会扭曲需求。3个项目都没有讨论"追问的引导性风险"。

**解法**：追问格式规范中增加"开放优先"原则——能开放问的先开放问，只在老板明确说不出偏好时才给推荐+yes/no。

### ANGLE-008 防糊弄

**风险1：军师维度分析糊弄**
军师收到老板指令后返回维度清单，但怎么验证军师真的逐个维度分析过、不是随便列几个？如果军师只返回3个维度说"其他已覆盖"，秘书无法判断这3个是否完整。

**解法**：军师输出必须包含完整覆盖矩阵（所有适用维度 + 每个维度的覆盖状态 + 判断依据），不能只返回"需追问的维度"。秘书看到完整矩阵才能判断军师有没有漏。

**风险2：秘书追问糊弄**
秘书拿了清单，但可能没问全就交给PM。追问结果文件里怎么证明每个维度都处理了？

**解法**：追问结果文件必须包含完整维度表（每个维度标注：已确认/默认值assumption/老板跳过），不能只写问答记录。

**风险3：默认值当确认值**
不重要的维度填默认值标(assumption)，但PM可能没注意到(assumption)标记，把假设当确认需求来执行。

**解法**：追问结果文件中(assumption)值必须用醒目格式标注（如加粗或单独列出），PM派发prompt中提醒"注意(assumption)标记的值是假设需PM验证"。

### ANGLE-017 反面论证

**如果维度清单设计是错的，它会掩盖什么问题？**

假设7个核心维度漏了某个关键维度（比如"风险与依赖"），那么所有任务都会漏问这个维度，但没人发现——因为清单上没有它，秘书不会觉得缺了什么。这比"问了但问错了"更危险，因为"没问"是沉默的。

**验证方法**：用3个不同场景（软件开发/市场调研/性能优化）各跑一遍维度清单，检查是否有"该问但清单上没有"的维度。如果3个场景都有同一个缺口，说明清单设计有遗漏。本方案在维度设计时已执行此验证（见第三节验证表）。

**如果"军师只返回维度清单不返回分析"是错的？**

军师只返回维度名和覆盖状态，不返回"为什么这个维度需要追问"的分析。如果秘书不理解为什么问这个问题，可能问得不到位（比如只问"成功标准是什么"而不追问"怎么验证"）。

**缓解**：技能文件中每个维度附带"追问要点"（该维度具体要问什么），秘书按要点追问。军师不解释为什么，但技能文件保证问到位。

### ANGLE-022 机器执行优先

**哪些环节可以机器执行？**

| 环节 | 能否机器执行 | 说明 |
|---|---|---|
| 维度清单定义 | 否 | 需要人工设计，但定义后是静态文件 |
| 场景分类 | 半自动 | 军师分析判断，但可基于关键词辅助 |
| "已覆盖"判断 | 否 | 需要语义理解，关键词匹配不可靠 |
| 追问执行 | 否 | 需要秘书与老板对话 |
| 追问结果记录 | 是 | 格式固定，可标准化为markdown模板 |
| 追问结果交接PM | 是 | 文件路径固定，PM派发prompt模板化 |

**结论**：维度清单和追问格式规范必须是**预定义的静态文件**（templates/probing-skill.md），而不是每次让军师从零生成。军师只做"动态判断"部分（场景分类 + 覆盖判断 + 输出矩阵），技能文件提供"静态规范"部分。这样军师的输出可以很短（只返回矩阵），大部分信息在技能文件里。

## 二、三个开源项目借鉴对比

### 项目1：prd-maker（jcmaker/prd-maker）

| 维度 | 借鉴了什么 | 为什么不直接照搬 |
|---|---|---|
| 8要素覆盖检查清单 | 结构化维度清单的思路——不是随便问而是有必填维度checklist | 8个维度全为软件开发导向（Problem/Target user/Core features/Technical constraints等），我们的场景含调研/分析/优化，需要通用维度 |
| 一次问一个问题 | 降低老板认知负荷，允许聚焦回答 | 直接采用，无修改 |
| 已答跳过 | 避免重复追问已覆盖维度 | 直接采用，但补充"已覆盖"硬标准（prd-maker没定义什么算已答） |
| "不知道"给推荐+一句话理由+yes/no | 降低老板决策成本 | 直接采用 |
| 不重要的填默认值标(assumption) | 区分确认值和假设值 | 直接采用，但增加醒目标注防PM误读 |
| 最多10问 | 设上限防追问疲劳 | 不照搬10——我们有场景分类（核心7维+附加最多3维=最多10维），但"已答跳过"后实际追问通常远少于10。上限改为8（理由见数字汇总） |

### 项目2：requirements-agent（merleezy/requirements-agent）

| 维度 | 借鉴了什么 | 为什么不直接照搬 |
|---|---|---|
| 追问后质量检查（Critique + Final Review） | 追问完不是直接用，要检查答案质量 | 多代理流水线（Clarify→Draft→Critique→Revise→Final Review）对我们太重——我们是技能不是独立系统，秘书一个人完成追问+检查，不需要5阶段流水线 |
| 5维rubric（unambiguous/atomic/testable/scoped/traceable） | 用于检查追问结果质量——每个维度的回答是否清晰/原子/可测/有范围/可追溯 | 5维rubric是检查需求文档质量的，不是追问维度设计。我们借用它来检查追问**结果**的质量（追问完用这5条快速检查每个答案），但维度设计另搞 |
| 最多2轮 | 控制追问轮次 | 直接采用（理由见数字汇总） |
| 每个问题可跳过 | 尊重老板"不想回答"的意愿 | 直接采用，跳过的维度填默认值标(assumption) |
| 不同模型档位（Balanced/Budget/Max quality） | 无 | 我们的架构不涉及多模型选择，不适用 |

### 项目3：interview-agent（jeremy-newhouse/interview-agent）

| 维度 | 借鉴了什么 | 为什么不直接照搬 |
|---|---|---|
| 量化导向（把"快"变成"延迟<3s"） | 追问时把模糊描述量化——追问不仅是"问什么"，还要"问到什么粒度" | 直接采用，纳入追问格式规范（量化追问原则） |
| 挑战假设问"为什么"深挖 | 追问不是只收集信息，还要挑战老板的假设 | 直接采用，但控制深度——我们用固定2轮上限替代follow_up_depth参数 |
| 完成判定标准 | 知道什么时候追问够了 | 直接采用，本方案定义了"追问完成"的判定标准 |
| 10阶段结构化访谈 | 结构化分阶段的完整性思路 | 10阶段全为软件开发（Integration Boundaries/Security & Auth/Performance & Scale/Error Handling等），非软件任务不适用。我们提取通用的，软件特有的降为场景附加维度 |
| 产出多文档（需求+决策日志+风险登记+待确认问题） | 多维度产出思路 | 4个文档太重。我们只产出1个文件（probing-result），其中包含：确认需求+默认假设+待PM验证项 |
| follow_up_depth参数 | 无 | 对我们太复杂，用固定2轮上限替代 |
| 可自定义阶段和问题 | 无 | 我们用场景分类+预定义维度替代自定义 |

## 三、追问技能方案

### 1. 维度清单设计

#### 设计原则

- 通用优先：核心维度适用于任何任务类型（软件/调研/分析/优化），不绑定具体场景
- 场景附加：非通用维度按任务类型追加，避免对非软件任务问软件特有问题
- 每维有标准：每个维度定义"已覆盖"硬标准，不靠军师感觉判断

#### 核心维度（7个，适用于所有任务）

| # | 维度 | 追问什么 | "已覆盖"硬标准 | 默认值（老板不回答时） |
|---|---|---|---|---|
| C1 | 目的与动机 | 为什么要做这个？解决什么问题？ | 老板说明了"为什么做"（不只是"做什么"），有明确的问题或动机描述 | (assumption) 按老板指令字面理解，PM推断动机 |
| C2 | 目标对象与场景 | 谁用？什么场景下用？ | 老板说明了使用者或使用场景（至少一个） | (assumption) PM根据任务类型推断目标用户 |
| C3 | 范围与边界 | 做什么？不做什么？ | 老板说明了"做什么"且至少暗示了"不做什么"（或范围足够明确不需追问边界） | (assumption) 范围=老板指令字面内容，边界=PM推断 |
| C4 | 成功标准 | 什么算"做完了"？怎么验证？ | 老板说明了可验证的完成标准（能用具体指标或测试方法判断"做完了"） | (assumption) PM制定验收标准后报老板确认 |
| C5 | 约束条件 | 有什么限制？（技术/资源/时间/数据） | 老板说明了至少一类约束（技术栈/时间/资源/数据来源） | (assumption) 无硬约束，PM按常规方案设计 |
| C6 | 优先级 | 先做什么？什么最重要？ | 老板说明了优先顺序或最重要的部分 | (assumption) PM按逻辑顺序拆解，报老板确认 |
| C7 | 输入与产出 | 处理什么信息？产出什么？ | 老板说明了输入数据/信息和产出物（两者都需明确） | (assumption) 输入=PM调研后确定，产出=按任务类型推断 |

**7个维度的理由**（为什么是7不是6或8）：
- prd-maker 8要素中"Core features"和"Non-goals"可合并为"范围与边界"（做什么+不做什么是一个维度的两面），"Data/content"与"输入与产出"等价。合并后8→7。
- interview-agent 10阶段中4个软件特有阶段（Integration/Security/Performance/Error Handling）不通用，移入场景附加。剩余通用维度提取后也是7个。
- 不能再减：去掉C1（目的）→可能解决错误问题；去掉C4（成功标准）→无法判断完成；去掉C3（范围）→范围蔓延。每个维度解决一个独立问题，无冗余。
- 不能再加：C1-C7已覆盖"为什么/谁/做什么/做完标准/限制/先做什么/输入输出"7个基本问题，任何任务类型都需要这7个。

#### 场景附加维度（按任务类型追加，最多3个）

| 场景 | 附加维度 | 追问什么 | "已覆盖"硬标准 |
|---|---|---|---|
| 软件开发 | S1 技术栈与架构 | 用什么技术/框架/架构模式？ | 老板指定了技术栈或架构方向 |
| 软件开发 | S2 安全与权限 | 认证/授权/数据安全有什么要求？ | 老板说明了安全要求或明确说"暂不考虑" |
| 软件开发 | S3 异常与性能 | 性能要求？错误处理要求？并发量？ | 老板说明了性能指标或错误处理要求 |
| 调研/分析 | R1 方法论与信源 | 用什么研究方法？数据从哪来？ | 老板指定了研究方法或数据来源 |
| 调研/分析 | R2 结论形式与深度 | 报告什么格式？分析到什么深度？ | 老板指定了产出格式或分析深度要求 |
| 优化/改进 | O1 现状基线 | 当前状态是什么？（需量化） | 老板提供了当前状态的量化数据 |
| 优化/改进 | O2 优化目标量化 | 目标是什么？（需量化，如"延迟<3s"） | 老板给出了量化的优化目标 |

**附加维度数量的理由**（为什么最多3个）：
- interview-agent 10阶段中有4个软件特有（Integration Boundaries / Security & Auth / Performance & Scale / Error Handling）。其中"Integration Boundaries"（集成边界）已被核心维度C5（约束条件）和C7（输入与产出）覆盖（集成边界本质是"跟谁对接+输入输出什么"），不需单列。剩余3个（Security / Performance / Error Handling）中，Performance和Error Handling可合并为"异常与性能"（都是非功能性要求）。所以软件场景附加3个。
- 调研和优化场景的附加维度从interview-agent的"Validation"（验证）和"Tradeoffs"（权衡）阶段提取，但验证已被核心C4（成功标准）覆盖，权衡是分析过程中自然产生的不是追问维度。所以只提取方法论和结论形式2个。
- 7核心+3附加=10最大维度数。配合"已答跳过"和8问上限，3是附加维度的上限——超过3个则7+4=11，即使老板指令覆盖2个仍有9个需追问，超过8问上限。

#### 场景分类标准（军师判断用）

| 场景 | 判断关键词 | 附加维度 |
|---|---|---|
| 软件开发 | 开发/功能/接口/页面/系统/API/前端/后端/数据库 | S1/S2/S3 |
| 调研/分析 | 调研/分析/研究/评估/对比/报告/市场/竞品 | R1/R2 |
| 优化/改进 | 优化/改进/提升/加速/降低/减少/性能 | O1/O2 |
| 其他/混合 | 不明确归属以上任一 | 无附加（只问核心7维） |

**场景分类由军师判断，秘书可覆盖**。如果军师判错场景（比如把调研任务判成软件开发），秘书在看到覆盖矩阵时可纠正。

#### 三场景验证（ANGLE-017反面论证要求）

用3个不同场景跑一遍维度清单，检查是否有"该问但清单没有"的缺口：

| 场景 | 指令示例 | 7核心维度是否够 | 附加维度是否够 | 缺口 |
|---|---|---|---|---|
| 软件开发 | "做一个用户管理功能" | 够（目的/对象/范围/标准/约束/优先级/IO全覆盖） | S1/S2/S3覆盖技术/安全/性能 | 无 |
| 市场调研 | "调研XX市场规模" | 够 | R1/R2覆盖方法/结论形式 | 无 |
| 性能优化 | "优化首页加载速度" | 够 | O1/O2覆盖基线/目标 | 无 |

3个场景均无缺口，维度清单设计通过反面论证验证。

### 2. 追问格式规范

#### 基本规则

| 规则 | 内容 | 理由 |
|---|---|---|
| 一次一个问题 | 每次只问1个维度，老板回答后再问下一个 | prd-maker验证过：一次问多个会导致老板只答容易的、跳过难的 |
| 多选题优先但不强制 | 能给选项的先给选项（A/B/C），但允许老板自由回答 | 多选题降低决策成本；但不强制因为有些维度不适合选择题（如"目的是什么"） |
| 已答跳过 | 军师覆盖矩阵中标"已覆盖"的维度不追问 | 避免重复追问已明确的信息，节省老板时间 |
| 开放优先 | 能开放问的先开放问（"你对XX有什么想法？"），只在老板说不出偏好时才给推荐+yes/no | 防止追问引导性扭曲老板意图（ANGLE-005盲区4） |
| 量化追问 | 老板给模糊描述时追问量化（"快"→"延迟<多少秒？"） | interview-agent的量化导向：模糊标准=不可验收 |
| "不知道"处理 | 老板说"不知道/你看着办"→秘书给推荐+一句话理由→只要yes/no。老板确认→标(assumption-confirmed)。老板不确认→标(assumption) | prd-maker机制：降低老板决策成本同时不放弃维度覆盖 |
| 可跳过 | 老板明确说"这个不用问"→标(skipped)→填默认值(assumption) | requirements-agent机制：尊重老板意愿 |
| 上限8问 | 单轮最多追问8个维度。超出按优先级截断 | 见数字理由 |
| 最多2轮 | 第1轮问所有未覆盖维度。第2轮只追问第1轮回答中仍模糊的 | requirements-agent机制：1轮可能不够（答案模糊），3轮以上说明追问方式有问题 |

#### 优先级排序（超过8问时截断用）

当未覆盖维度超过8个时，按以下优先级保留前8个：

1. C4 成功标准（无验收标准=无法判断完成=最高风险）
2. C3 范围与边界（无边界=范围蔓延=返工源头）
3. C1 目的与动机（无目的=可能解决错误问题）
4. C5 约束条件（无约束=可能提出不可行方案）
5. C6 优先级（无优先级=可能先做次要的）
6. C7 输入与产出（无IO=不知道处理什么产出什么）
7. C2 目标对象与场景（无对象=可能做给错误受众）
8. 场景附加维度（按场景重要性排）

**排序理由**：成功标准和范围边界不明确直接导致返工（成本最高），目的不明确导致方向错误（影响最大），约束和优先级影响方案可行性，IO和对象影响较小（PM可在Phase 1推断）。附加维度排最后因为核心维度没搞清楚时附加维度问了也没用。

#### 追问完成判定标准

满足以下全部条件，追问结束：
1. 所有核心维度（C1-C7）都有状态（已覆盖/已确认/assumption/skipped）
2. 场景附加维度都有状态
3. 已确认的维度中无模糊回答（如果有，进入第2轮追问）
4. 达到2轮上限后仍有模糊的→标(assumption)并记录到待PM验证清单

### 3. 技能形态

#### 技能是什么

追问技能 = **1个预定义markdown文件** + **军师动态输出的覆盖矩阵**。

- **静态部分**（技能文件）：维度定义、追问格式规范、覆盖标准、默认值。预定义好，军师不每次重新生成。秘书读取后按格式执行。
- **动态部分**（军师输出）：针对每次老板指令的覆盖矩阵——哪些维度已覆盖、哪些需追问、场景分类。军师每次调用时分析产出。

#### 文件位置

```
/workspace/.team/templates/probing-skill.md
```

**为什么放templates/目录**：
- templates/已存放所有角色模板，秘书习惯从此目录读取模板文件
- 不需要新建目录（不改基础设施）
- probing-skill.md是秘书用的技能参考文件，与角色模板同级别

#### 文件内容结构

```markdown
# 追问技能（Probing Skill）

> 维护者：军师 ｜ 秘书读取后按格式执行

## 使用条件
（何时触发追问、何时不触发）

## 维度清单
### 核心维度（7个）
（每个维度：名称/追问要点/已覆盖标准/默认值）
### 场景附加维度
（按场景分组的附加维度）

## 追问格式规范
（一次一个/多选题/开放优先/量化追问/不知道处理/跳过处理/上限/轮次）

## 军师输出格式
（覆盖矩阵模板——军师按此格式输出，秘书按此格式读取）

## 追问结果文件格式
（probing-result模板——秘书按此格式记录追问结果）

## 追问完成判定标准
（全部条件）

## 追问结果质量检查
（用requirements-agent的5维rubric快速检查每个答案）
```

#### 秘书怎么调用

1. 收到老板指令 → 判断是否需要追问（见第4节触发时机）
2. 需要追问 → 派发军师，输入老板原始指令
3. 军师返回覆盖矩阵 → 秘书读 templates/probing-skill.md 获取追问格式规范
4. 秘书按矩阵中"需追问"的维度，一次一个追问老板
5. 追问完成 → 秘书按技能文件中的结果文件格式，写入 status/probing-result-{project}.md
6. 派发PM时prompt中指定"读 status/probing-result-{project}.md 获取已确认需求"

#### 维护者

- **技能文件**（templates/probing-skill.md）：军师维护。维度清单调整、格式规范更新由军师负责（走提案前置检查，因为涉及维度定义变更=结构性变更）。
- **覆盖矩阵**（军师每次输出）：军师按技能文件中定义的格式输出，不每次重新设计格式。

### 4. 军师调用方式

#### 触发时机

**触发条件**（满足任一即触发）：
1. 秘书收到老板新指令，且指令中缺少C4（成功标准）或C3（范围与边界）的覆盖——这两个维度缺失风险最高
2. 秘书收到老板新指令，判断指令模糊（主观判断，但"模糊"的最低标准是：指令少于20字且不含任何约束/标准/对象描述）
3. 秘书主动判断需要追问（任何秘书认为需要澄清的情况）

**不触发的情况**：
- 老板指令是跟进/修改已有任务（已有probing-result文件）
- 老板指令是简单Q&A或状态查询
- 老板明确说"不用问了直接做"
- 秘书判断指令足够详细（所有7个核心维度都有明确信息）

**灰色地带**：触发条件2中"少于20字"是硬标准，但"模糊"的判断仍有主观成分。如果秘书不确定，倾向触发（成本只是一个子代理调用，漏追问的成本是返工）。详见第七节灰色地带。

#### 输入

军师收到的输入：
```
【老板原始指令】
{老板的原始指令文本，不做任何加工}
```

军师不需要读其他文件——只分析指令文本本身。维度定义在技能文件中，军师已熟知（军师是技能文件维护者）。

#### 输出

军师返回的覆盖矩阵（格式固定）：

```
场景分类：{软件开发/调研分析/优化改进/其他}
适用维度：核心7 + 附加{N}

| # | 维度 | 覆盖状态 | 判断依据 | 需追问 |
|---|---|---|---|---|
| C1 | 目的与动机 | 未覆盖 | 指令只说"做什么"未说"为什么" | 是 |
| C2 | 目标对象与场景 | 已覆盖 | 指令提到"给运营团队用" | 否 |
| C3 | 范围与边界 | 未覆盖 | 指令只说"做用户管理"未说边界 | 是 |
| ... | ... | ... | ... | ... |
| S1 | 技术栈与架构 | 未覆盖 | 指令未提技术栈 | 是 |

需追问维度数：{N}（≤8则全部追问，>8则按优先级截断前8）
默认值建议：
- {维度名}：推荐"{默认值}"，理由：{一句话}
```

**输出约束**：
- 只返回矩阵+默认值建议，不返回分析过程（省上下文）
- 矩阵必须包含所有适用维度（不只是需追问的），供秘书验证完整性（ANGLE-008防糊弄）
- 判断依据必须是一句话具体说明（不能写"未覆盖"不解释）

#### 调用频率控制

| 控制项 | 规则 | 理由 |
|---|---|---|
| 每个新指令最多调用1次 | 同一指令不重复调用军师分析维度 | 军师分析是基于指令文本的静态分析，重复调用结果相同 |
| 追问过程中不调用军师 | 秘书追问时如遇新问题，自己判断或记录待确认 | 追问中调军师=每次都跟老板对话的开销，违背设计初衷 |
| 不计入角度库维护调用 | 本次调用是任务分析不是角度库维护 | 但计入"军师被调用总次数"（计数器+1），影响meta-audit/整理触发 |

**灰色地带**：追问技能调用是否计入"军师被调用总次数"？如果计入，会加速meta-audit触发频率（每10次）。建议计入——军师确实被调用了做了实质工作。但这意味着如果每条老板指令都触发追问，meta-audit会频繁触发。实际中不是每条指令都触发追问（只在模糊时触发），所以影响可控。

#### 与军师6个触发点的关系

军师现有6个触发点：
1. 秘书识别到新角度时（事件驱动）
2. 每个项目周期结束（定期整理）
3. 角度库超过50个角度时（紧急）
4. 子代理产出需军师验证时（R4关卡）
5. 每10次调用触发meta-audit
6. 每50次调用触发整理

**追问技能是第7个触发点**：收到老板新指令且判断需追问时。

| 与现有触发点的关系 | 说明 |
|---|---|
| 与#1（新角度）的关系 | 追问过程可能发现新角度（如"这类任务总缺XX维度"）→ 喂给#1触发新角度提案 |
| 与#2/#6（整理）的关系 | 追问调用计入军师总次数 → 加速#5/#6触发 |
| 与#3（紧急）的关系 | 无直接关系 |
| 与#4（R4验证）的关系 | 无直接关系（追问是输入侧，R4是产出侧） |
| 与#5（meta-audit）的关系 | 追问调用+1 → 加速meta-audit触发。实际影响可控（不是每条指令都触发追问） |

**不冲突**：追问触发点服务于"任务分析"（输入侧），现有6个触发点服务于"角度库维护"（进化侧）。两者目的不同，互不干扰。追问触发点可能feed into角度库进化（发现新角度），形成正向循环。

#### 与宪法1.4.5的关系

宪法1.4.5："收到老板需求后，如果发现模糊点，先列出选项问老板确认，确认后再派PM。"

追问技能是1.4.5的**操作化实现**：
- 1.4.5说"发现模糊点"——追问技能定义了"模糊点"=维度未覆盖
- 1.4.5说"列出选项问老板"——追问技能定义了"怎么问"=一次一个+多选+推荐
- 1.4.5说"确认后再派PM"——追问技能定义了"确认结果怎么传给PM"=probing-result文件

追问技能不改变1.4.5的规则，只是把它从一句话原则变成可执行的流程。

### 6. 自适应机制

#### 机制1：已答跳过（指令详细度自适应）

| 指令详细度 | 军师覆盖矩阵结果 | 秘书追问量 |
|---|---|---|
| 非常详细（7核心维度全覆盖） | 全部"已覆盖" | 0问，直接派PM |
| 部分详细（覆盖3-5个维度） | 部分未覆盖 | 2-4问 |
| 模糊（覆盖0-2个维度） | 大部分未覆盖 | 5-8问（触发上限） |

这是核心自适应机制——不需要额外参数，"已答跳过"本身就实现了按指令详细度调整追问深度。

#### 机制2：场景分类（任务类型自适应）

军师根据指令关键词判断场景，选择不同的附加维度。软件开发问S1/S2/S3，调研问R1/R2，优化问O1/O2。不需要秘书手动选择场景。

#### 机制3：不采用技术水平检测

prd-maker检测用户技术水平（开发者/非开发者）调整用词。我们**不采用**，理由：
- 我们的"用户"始终是老板一个人，老板的技术水平不变
- 秘书追问时已使用大白话（ANGLE-006），不需要按技术水平调整
- 技术水平检测增加复杂度但对我们场景无收益

#### 机制4：追问深度自适应

- 第1轮：问所有未覆盖维度（广度优先）
- 第2轮：只追问第1轮中回答仍模糊的维度（深度优先）
- 如果第1轮所有回答都清晰→不进入第2轮（省时间）
- 如果第1轮回答都模糊→第2轮全部重问（可能追问方式有问题，秘书调整问法）

### 7. 风险和约束

#### 风险清单

| # | 风险 | 严重度 | 缓解策略 |
|---|---|---|---|
| R1 | 军师场景分类错误（把调研判成软件开发） | 中 | 秘书在看到覆盖矩阵时可纠正；附加维度问错了最多浪费2-3个问题，不致命 |
| R2 | "已覆盖"判断错误（军师认为已覆盖但实际模糊） | 高 | 每个维度有硬标准+判断依据一句话；秘书看到矩阵后可质疑任何"已覆盖"判断 |
| R3 | 追问引导性扭曲老板意图 | 中 | 开放优先原则——能开放问的不给选项；只在老板说不出偏好时才给推荐 |

| R7 | 军师角色扩展超出"角度库管理"边界 | 中 | 见灰色地带G1 |

## 四、数字理由汇总

| 数字 | 值 | 理由 |
|---|---|---|
