## 一、老板的需求

老板原话要点：
1. 追问这件事应该有一个单独的角色去做，但**作为技能存在，不是独立角色**
2. 因为最终追问老板的人是秘书——"最终追问我的人是你"
3. 如果每次调用军师都要跟老板对话，开销太大
4. 军师在后台分析维度出清单，秘书拿清单前台追问老板

## 二、设计约束

1. **追问执行者是秘书**：秘书拿着维度清单追问老板，不需要军师直接跟老板对话
2. **维度分析者是军师**：军师收到老板的原始指令后，在后台分析出"该问哪些维度"，返回维度清单
3. **技能化**：不是独立角色，是秘书调用的技能（类似prompt模板+检查清单）
4. **省上下文**：军师只返回维度清单（不是完整分析），秘书拿清单追问，追问结果直接进入需求文档

## 三、参考资料

老板要求调研GitHub上专门做追问的开源项目，秘书找到了3个高度相关的项目。军师需要参考它们的机制设计我们的追问技能。

### 项目1：prd-maker（jcmaker/prd-maker）

- GitHub: https://github.com/jcmaker/prd-maker
- 类型：Claude Code/Codex插件
- 核心机制：
  - **自适应访谈**：检测用户技术水平（开发者/非开发者），调整问题用词
  - **8要素覆盖检查清单**：不是随便问，而是有8个必填维度的checklist
  - 已答的维度跳过，只追问没覆盖的
  - 一次问一个问题，最多10问
  - 不重要的填默认值标`(assumption)`
  - "我不知道"时给一个推荐+一句话理由，只要yes/no

- 8要素清单：
  | # | 维度 | 追问什么 |
  |---|---|---|
  | 1 | Problem | 为什么要做（用于后续消歧） |
  | 2 | Target user | 谁用、什么场景 |
  | 3 | Core features | 做什么（3-7个） |
  | 4 | Non-goals | 不做什么（你没提它主动提案候选） |
  | 5 | Success criteria | 什么算"做完了" |
  | 6 | Technical constraints | 技术栈/部署/数据 |
  | 7 | Priority | 先做什么 |
  | 8 | Data/content | 处理什么信息 |

- 产出：纯markdown PRD，7段结构，带结构linter（Python脚本验证）

### 项目2：requirements-agent（merleezy/requirements-agent）

- GitHub: https://github.com/merleezy/requirements-agent
- 类型：独立web应用（前后端分离）
- 核心机制：
  - **多代理流水线**：Clarify → Draft → Critique → Revise → Final Review
  - Clarify代理追问2-4个问题（最多8个，最多2轮），每个问题可跳过
  - Critique代理用5维rubric逐条检查每个功能需求：unambiguous, atomic, testable, scoped, traceable
  - Final Review：lead-engineer视角的go/no-go判定，检查5个一致性原则
  - 每个阶段可用不同模型（OpenRouter），有3档预设（Balanced/Budget/Max quality）

- 独有特点：
  - 追问后有**两道质量检查**（Critique + Final Review），不是问完就完
  - 支持局部修改和全局修改两种修订模式
  - 产出可交互PRD文档

### 项目3：interview-agent（jeremy-newhouse/interview-agent）

- GitHub: https://github.com/jeremy-newhouse/interview-agent
- 类型：Python CLI（Claude Agent SDK）
- 核心机制：
  - **10阶段结构化访谈**，比prd-maker多了4个维度
  - 一次一个问题，有追问深度（follow_up_depth参数）
  - 挑战假设，问"为什么"深挖
  - 量化导向：把"快"变成"延迟<3s"
  - 有完成判定标准

- 10阶段：
  | Phase | Focus |
  |---|---|
  | 1 | Problem Space |
  | 2 | User Journey |
  | 3 | Data Architecture |
  | 4 | Integration Boundaries |
  | 5 | Security & Auth |
  | 6 | Performance & Scale |
  | 7 | Error Handling |
  | 8 | Non-Functional |
  | 9 | Tradeoffs |
  | 10 | Validation |

- 产出4个文档：需求文档+决策日志+风险登记+待确认问题
- 可自定义阶段和问题（add_phase, add_question_pattern）

## 四、军师需要产出的方案

### 必须回答的问题

1. **维度清单设计**：参考3个项目的维度（prd-maker 8要素 / interview-agent 10阶段 / requirements-agent 5维rubric），设计我们自己的追问维度清单。需要考虑：
   - 我们的场景不限于软件开发（也可能是调研/分析/优化等任务）
   - 维度数量控制在多少合适（太多追问累，太少遗漏多）
   - 是否需要分场景（开发任务用一套维度，调研任务用另一套）

2. **追问格式**：每个维度怎么问？参考prd-maker的"一次一个问题+多选题优先+已答跳过"机制，设计追问格式。

3. **技能形态**：这个技能具体是什么形态？prompt模板？检查清单？还是一个markdown文件秘书读取后按格式执行？

4. **军师调用方式**：军师在什么时机被调用（收到老板指令后？还是秘书判断需要追问时？），调用时输入什么（老板原始指令），输出什么（维度清单）。

5. **和现有体系的关系**：追问技能产出确认后的需求，怎么衔接PM的角色（PM接手写需求文档）？追问技能和军师的6个触发点怎么配合？

6. **自适应机制**：prd-maker会检测技术水平调整用词。我们是否需要类似机制（比如判断老板给的指令详细程度，决定追问深度）？

### 产出格式

请按以下结构产出方案：

```
## 追问技能方案

### 1. 维度清单设计
（列出维度+每个维度的追问问题+判断"已覆盖"的标准）

### 2. 追问格式规范
（怎么问、一次问几个、多选题怎么设计、"不知道"怎么处理）

### 3. 技能形态
（技能是什么文件、存在哪里、秘书怎么调用）

### 4. 军师调用方式
（触发时机、输入、输出、调用频率控制）

### 5. 衔接机制
（追问结果→PM的交接点、与军师触发点的关系）

### 6. 自适应机制（如有）
（是否分场景/分深度）

### 7. 风险和约束
（这个方案的潜在问题）
```

### 约束

- 方案中所有数字（维度数/问题数/上限）必须有理由，不能拍脑袋
- 参考3个项目时要说明"借鉴了什么+为什么不直接照搬"
- 如果有灰色地带（无法确定的设计选择），标注出来，不要猜
