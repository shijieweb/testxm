# 提案质量复盘：为什么DET融合方案来回讨论了3轮才落地

> 日期：2026-08-15
> 发起人：老板
> 目的：从DET融合方案的3轮讨论中提取规律，找出缺失环节，评估军师能否自改进

---

## 一、3轮讨论完整复盘

### 第1轮：我→老板（方案被退回）

**我提出的方案**：规则剪枝——"拦截次数=0连续2个整理周期→归档该DET（从清单移除）"

**老板退回原因**："这些规则不是分标签做的吗？他积累虽然说多，那我们只是合并，因为他既然能加进来，说明它确实有用，想办法把它融合是不是可行？"

**我的缺失**：直接跳到"删除"（破坏性方案），没有先考虑"融合"（保守性方案）。规则能加进来是因为踩过坑，踩过坑就有认知价值——我没有从"价值保留"角度思考。

### 第2轮：老板→我→军师→老板（军师审查发现6处问题）

**我提出的修订方案**：DET融合——A组(002←003+005+010)、B组(001←011)、C组(009+013→ANGLE)、D组(012←014)

**军师审查发现6处问题**：
1. A组覆盖不严格：DET-002增强版没有覆盖003的"≥2备选值对比"、005的"条数×单条平均字数"、010的"按结构定位读取"三个具体检测要点
2. C组不需要融入ANGLE：DET-009/013的内容**已经在ANGLE-024规则3和8中了**
3. D组归属勉强：012查"量溢出"、014查"质失效"，方向不同
4. DET数量算错：说6条实际7条
5. **漏了联动修改**：ANGLE-024有5条规则引用了被融合的DET编号，不更新会断链
6. **没回答原问题**：零拦截且无归属关系的DET（004/006/007/008）怎么办

**我的缺失**：
- 没有grep所有引用了待改DET的文件（漏了ANGLE-024的5条引用）
- 没有逐条比对被吸收方的检测方法+通过标准的每个要点（A组覆盖度不够就提了）
- 没有验证自己方案中的数字（DET数量算错）
- 没有回答"不能融合的零拦截DET怎么办"

### 第3轮：军师→我→老板（我复审军师又发现3处问题）

**我复审军师审查后发现3处问题**：
1. **军师DET数量也算错了**：说7条实际8条——军师在5.3节建议D组保持独立，但在6.3节又按D组融合算的7条，自相矛盾
2. **联动修改数量也受影响**：D组独立则只需更新4条规则不是5条
3. **军师漏了与ANGLE-024简化的协同效应**：如果ANGLE-024同时简化（删除规则2-9），那些DET引用随规则消失，不需要逐条更新——两个审批项各审各的，错过了合并执行的效率

**军师的缺失**：
- 自己也犯了数字错误（跟我的错误同类型）
- 没有检查跨提案协同（DET融合和ANGLE-024简化是两个并行审批项，有重叠）
- 审查时没有自验自己的结论（D组独立vs融合的矛盾没发现）

---

## 二、根因分析

### 表面问题：4类错误反复出现

| 错误类型 | 第1轮（我） | 第2轮（我） | 第3轮（军师） |
|---|---|---|---|
| 未考虑替代方案 | 删除→应先考虑融合 | - | - |
| 未做交叉引用检查 | - | 漏ANGLE-024的5条引用 | - |
| 未验证数字 | - | DET数量算错 | DET数量也算错 |
| 未检查跨提案协同 | - | - | 漏ANGLE-024简化协同 |

### 深层根因：提案流程缺少"前置检查"环节

当前军师的提案流程是：
```
发现问题 → 分析原因 → 设计方案 → 提交给老板/秘书
```

**缺失环节**：在"设计方案"和"提交"之间，没有"提案前置检查"步骤。直接从分析跳到提交，跳过了"验证方案本身的质量"。

具体缺失4项：

1. **替代方案强制考虑**：提方案前必须问"有没有比这个更保守的方案？"（破坏性→保守性）
2. **交叉引用强制扫描**：提方案前必须grep所有引用了待改项的文件，列出影响面
3. **跨提案协同检查**：提方案前必须检查当前是否有其他待审批提案与本提案重叠或协同
4. **数字强制自验**：提交前逐项验证方案中所有数字/计数是否正确

### 与现有机制的差异

| 现有机制 | 检查什么 | 不检查什么 |
|---|---|---|
| DET-007（方案自洽性） | 方案内容是否自相矛盾 | 方案是否考虑了所有影响面 |
| ANGLE-024（异常路径覆盖） | 设计是否有异常路径遗漏 | 提案本身的完整性和协同性 |
| 验证标准清单5项硬指标 | 新角度是否值得入库 | 结构性变更方案的质量 |

**结论**：现有机制都是检查"方案内容本身"的，没有检查"方案提交前是否做好了影响评估"。这是一个流程级规则，不是检测项。

---

## 三、给军师的问题

老板要求：军师评估自己能不能改进，避免下次提案再出现这种来回讨论。

**具体问题**：
1. 军师在提案前能否自动执行上述4项前置检查？
2. 如果能，这4项检查应该以什么形式落地（新规则/新DET/现有规则增强）？
3. 军师的自我审查（第2轮）能不能也加这4项检查，避免审查者自己犯同样的错？

---

## 四、我的初步建议（供军师参考）

在`js-cognitive-rules.md`的提案流程中增加"提案前置检查"规则：

```
### 提案前置检查（v2.15新增）
军师向老板/秘书提交任何结构性变更方案前，必须完成以下4项检查：

1. 替代方案考虑：至少考虑2个方案（1个破坏性+1个保守性），说明为什么选当前方案
2. 交叉引用扫描：grep所有引用了待改项的文件，列出影响面清单
3. 跨提案协同检查：检查当前是否有其他待审批提案与本提案重叠或可合并执行
4. 数字自验：逐项验证方案中所有数字/计数（如"融合后X条"→数一遍确认）

未完成前置检查的提案，不提交。审查他人提案时同样执行这4项检查。
```

这个规则不增加DET（刚做完DET融合减到8条，不宜马上加），而是作为管理规则的一部分，在提案流程中强制执行。
