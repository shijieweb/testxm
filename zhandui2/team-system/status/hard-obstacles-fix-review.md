## 一、硬障碍1审查：ISSUE-009 git仓库未初始化

### 1.1 现状核实（实测，非凭方案描述）

- 实测 `cd /workspace/.team && git status` → `fatal: not a git repository (or any parent up to mount point /)`。`.git` 不存在。方案描述属实。
- 实测 `.cache` 目录不存在。`.gitignore` 尚无需排除对象。
- `js-start.sh` 第168-172行：git 检查为 `[WARN]`，不设 `all_ok=0`。方案第3步"改FAIL"有据。
- `js-end.sh` 主流程（第187-209行）：`increment_counter` → `verify_refs` → 后续步骤提示。无 git commit、无缓存生成。方案第2步"加自动提交"有据。
- `js-cognitive-charter.md` 第85行：入库流程第1步"确认当前版本已提交到GitHub（git commit），作为可回滚基线"。规则要求存在，技术未实现——ISSUE-009 成立。
- `js-cognitive-framework.md` 变更记录第9行已标注 `[注：git仓库当时未初始化，实际备份未完成，ISSUE-009]`。假声明标注已部分启动。

**结论：方案对现状的描述全部属实，无虚假前提。**

### 1.2 关键设计决策逐条审查

| 设计决策 | 审查意见 | 理由 |
|---|---|---|
| 归档文件入git（需历史追溯） | **认可但提醒体积** | .archive 入git能给"归档文件被误改"兜底，价值真实。但 .archive 是"文件级归档"，git 是"版本级历史"，双重历史会让仓库随归档操作持续增长。当前 .archive 总量可控（self-review-archive 46KB + 两个 changelog 22KB + archived-angles 0.5KB），增长缓慢，可接受。建议每10个整理周期（500次调用）跑一次 `git gc` 压缩。 |
| .cache不入git（可重新生成） | **认可** | 缓存可由 js-end.sh 重新生成，不入git正确。 |
| 提交时机：js-end.sh收工时（计数器+1后） | **修改：放最后，verify_refs之后** | 方案说"计数器更新后、引用检查前"。但 verify_refs 不写文件（只读检查），放前放后不影响捕获的变更。逻辑上"所有收工写操作完成后提交"更清晰——放最后，verify_refs 之后。increment_counter 的 sed -i 是唯一写操作，commit 放它之后即可。 |
| 提交粒度：整体提交（军师单线程） | **认可** | 单线程无并发，整体提交无竞态。 |
| 提交失败只警告不阻断 | **认可，补闭环** | git 是保障不是必需，不阻断收工流程——哲学正确。但必须与第3步"--check改FAIL检测未提交变更"形成闭环：commit失败→下次--check检测到未提交→FAIL→倒逼修复。否则"警告"会像 DET-014 那样被静默跳过。方案已含第3步，闭环成立。 |

### 1.3 必改项（落地前必须补）

**必改1：git user.name/email 未配置——技术遗漏，会导致首次 commit 就失败**

`git commit` 需要提交者身份。当前环境未配置（实测无 .git，更无 config）。若不配，首次 `git commit` 报错 `Please tell me who you are`，方案第1步基线提交直接失败。

建议第1步追加：
```bash
git config user.name "军师体系"
git config user.email "military-advisor@team.local"
```
用 `git config`（非 `--global`）只配本仓库，不污染全局。

**必改2：.cache 路径与硬障碍3/cache-intelligence-review 不一致——必须统一**

- 本方案第1步 .gitignore 排除 `.cache/`（即 `/workspace/.team/.cache/`）。
- 硬障碍3方案第4步 `mkdir -p .cache`（同样是 .team/.cache）。
- 但 `cache-intelligence-review.md` 第233行写的是 `status/.cache/`（即 .team/status/.cache/）。

三处路径冲突。若 .gitignore 按 `.cache/` 排除，而实际缓存落在 `status/.cache/`，则 status/.cache 会被 git 跟踪——违背"缓存不入git"。

建议：统一为 `.team/.cache/`（不放 status 下，因为 status 是"按需读取的status文件"，缓存是"可丢弃的加速层"，语义不同，分开放更清晰）。.gitignore 写 `.cache/`。同步修正 cache-intelligence-review.md 第233行。并在 INDEX.md 新增 `.cache/` 条目（标注"按需读取/可丢弃/不入git"）。

### 1.4 提醒项（非阻断，建议处理）

**提醒1：logs/ 目录入git决策缺失。** .team/logs/2026-08-14/js-cognitive.log 存在。方案 .gitignore 只提 .cache/ 和 *.tmp，没提 logs/。日志是运行时产物（类似缓存可重新生成），建议入 .gitignore 排除；或明确"入git以便追溯"。需决策，不能默认。

**提醒2：基线提交message用"v2.15"——版本号要对齐。** framework 文件头最新变更记录是 v2.12，但提案前置检查标注"v2.15新增"。"v2.15"指体系整体版本。基线 message 用 v2.15 可接受，但建议在 framework 文件头变更记录补一条"v2.15：git仓库初始化"使版本号有据。

**提醒3：历史假声明标注完整性需核实。** 方案说"v2.8~v2.12共5处假声明"。framework 第9行已标注1处。需逐一确认其余4处是否都已标注 `[注：ISSUE-009]`，避免遗漏。

### 1.5 更简单的替代方案？

无。git init + 自动 commit 是版本回滚的标准做法，ANGLE-019 可逆性的技术实现就靠它。没有更简单的等价替代。认可方案路径。

### 1.6 硬障碍1结论：修改后认可

## 二、硬障碍2审查：DET-002形式合规实质失效3次达阈值

### 2.1 核心问题判断——认可且赞赏

方案精准识别了根因：**Check 2"数完一遍再数一遍"是同一个人用同样的认知盲区数两遍，相关性错误**。这与军师在 cache-intelligence-review.md 和自回顾序号009中的判断一致——军师"查别人的数字错误能抓到（审助手报告时抓到），自己的数字错误抓不到（审自己时也数错）"。

方案明确"不要求军师更仔细（3次前科证明不可靠）""不增加新DET/新角度（根因不是缺认知，是缺执行工具）"——这两条决策非常清醒，符合 ANGLE-022 精神（错误转检测项，不是错误转检讨），也符合 DET 融合后"从12减到8条"的精简方向。**强烈认可。**

### 2.2 关键设计决策逐条审查

| 设计决策 | 审查意见 | 理由 |
|---|---|---|
| 自动化验证优先（能机器数不要手数） | **强烈认可** | 用不会犯认知盲区错误的机器替代有3次前科的人，是正解。符合"根因是缺执行工具不是缺认知"的判断。 |
| 可grep计数用命令行自动计数 | **认可，但grep模式须先验证** | 见下方遗漏1——方案给的示例模式有过宽风险（DET-012变体）。 |
| 无法自动化的数字标注"估算值非实测" | **认可** | 诚实标注，让读者知道可靠性边界。 |
| 二次验证：自动化不需要、人工必须 | **认可** | 逻辑正确：机器不会数错（前提是模式对），人工会。 |
| 方案推算（12-4=8）用grep数实际条数反验 | **认可** | 把"逻辑推算结果"用"事实计数"反验，是 DET-002 检测方法增强的正确延伸。 |

### 2.3 必改项

**必改1：grep 模式有过宽风险——须先验证匹配范围（这是 DET-012 的变体）**

方案给的自动化验证示例模式有问题，恰恰会重犯 DET-012"grep过宽"：

- `grep -c '^| DET-' js-self-review.md`：会同时匹配"检测项清单"表（第73行起）和"DET分层标注"表（第88行起），两表都是 `| DET-xxx |` 格式。结果会高估约1倍。需锚定到检测项清单区块（如用 awk 限定行范围，或用更精确的列数过滤——js-start.sh 已用 `awk -F'|' 'NF>=7 && $2~det'` 过滤8字段行，可复用此思路）。
- `grep -c '^### ' js-cognitive-rules.md`：匹配的是"小节数"不是"规则条数"。rules.md 的 ### 是管理规则小节标题（新增角度/识别复核/验证标准清单...），不是"规则条数"。语义要对齐——到底验的是"小节数"还是"规则数"？需明确。
- `grep -c '^### ANGLE-' js-cognitive-framework.md`：相对准确（角度定义用 ### ANGLE-XXX），但需确认候选/待验证区是否用同格式，避免把候选角度数算进去。

**建议追加一条规则**：自动化验证的 grep 模式，必须先用实际文件验证匹配范围正确（贴出命令+输出+人工确认匹配的是目标区块），才能用于 Check 2。否则"用机器数"会数错——这又是 DET-012 的教训。这本身就是一次 DET-012 的拦截机会。

**必改2：可靠性分层百分数（95%/70-80%/60%）本身是估算值——递归犯 DET-002**

方案第3步给自动化验证"约95%可靠性"、人工二次"约70-80%"、人工单次"约60%"。这三个百分数哪来的？没有计算过程、没有实测依据——**这恰恰是 DET-002"提数字没算实际效果"的再次重演**。

这是一个有趣的递归问题：**用不可靠的估算数字去说明"数字不可靠"**。军师作为审查者必须指出这个自指矛盾。

建议二选一：
- （推荐）去掉具体百分数，改用定性分级："自动化验证=高可靠 / 人工二次=中 / 人工单次=低"，并在该分级旁标注"本分级为定性判断，非实测百分数"。
- 或者保留百分数但标注"以下百分数为估算值非实测"（符合方案自己第1步"无法自动化的数字标注估算值"的原则——那么可靠性分层的百分数也该遵守自己的规则）。

### 2.4 提醒项

**提醒1：自动化验证也要防"形式合规"。** 军师可能写了 `grep -c` 命令但没真正运行，或运行了没看结果就写"已验证"。这是 DET-002 形式合规的变体。建议 Check 2 要求：自动化验证必须**贴出命令 + 贴出实际输出结果**，证据可复现，不能只写"已用grep验证"。

### 2.5 更简单的替代方案？

有一个增强方向（非替代）：把"关键数字自动统计"直接做进 `js-start.sh --check`（或开工输出），军师每次开工就能看到机器算的真实 DET数/角度数/规则数，对照方案里的数字。这比依赖军师"自觉跑grep"更可靠——不靠军师自律（DET-002前科），靠脚本。但这属于锦上添花，方案本身的"Check 2加自动化路径"已解决核心问题。可作为后续增强项。

### 2.6 硬障碍2结论：修改后认可

根因判断和"不增加DET/不要求更仔细"的决策非常到位。落地前补必改1（grep模式验证）、必改2（百分数改定性或标注估算）。这是本审查中方向最准的一个方案。

## 三、硬障碍3审查：缓存过期绝不能静默使用

### 3.1 现状核实

- 实测 `.cache` 目录不存在。缓存尚未生成过。
- `js-start.sh` 当前开工流程无任何"读缓存"逻辑——[5/7]步直接 `head -15 framework` + `grep "^### " rules`，不读 .cache。
- `js-end.sh` 无缓存生成逻辑。
- `cache-intelligence-review.md` 已建议"--check增加hash校验"（第238-244行）和"缓存过期不静默用"（第234行）。硬障碍3方案与之一致。
- DET-014（js-self-review.md 第82行）已要求"grep空返回检测+警告"。方案第5步"DET-014扩展到缓存场景"是合理延伸。

**重要前置事实**：当前根本没有任何缓存被使用。这个方案是为"未来要加的缓存"提前建保障。这意味着方案的收益完全取决于"缓存未来是否被加"——而 cache-intelligence-review.md 已大幅下调缓存收益评估（"缓存只能省读取不省思考，收益被高估"）。老板已决定推进缓存，故保障机制是必须配套。本审查聚焦"保障机制本身是否可靠"，不重复评估缓存收益。

### 3.2 关键设计决策逐条审查

| 设计决策 | 审查意见 | 理由 |
|---|---|---|
| 缓存过期回退读源文件，不报错停止 | **强烈认可** | "缓存是加速手段不是必需品"——哲学正确，与 cache-intelligence-review.md 立场一致。过期不阻断，降级读源。 |
| hash校验而非时间过期 | **认可** | 源文件没变缓存就不过期、变了立刻过期，比时间过期精确。md5 对于完整性校验足够（不做安全防篡改）。 |
| 元数据头标准化（source_path/source_hash/generated_at/expires:never） | **认可，改相对路径** | 格式合理。但 source_path 用绝对路径（`/workspace/.team/...`）不健壮——.team 若迁移则失效。建议改相对路径（相对 .team 根，如 `memory/js-cognitive-framework.md`），脚本拼绝对前缀。 |
| 缓存生成在收工时（git commit后） | **认可** | 依赖硬障碍1的 git commit 先完成，顺序正确。 |
| 缓存不入git | **认可** | 与硬障碍1的 .gitignore 一致（前提是路径统一，见硬障碍1必改2）。 |

### 3.3 必改项——最大遗漏

**必改1：未诚实区分"脚本校验"与"军师自觉校验"的可靠性差异**

方案第2步"军师/脚本读取缓存时必须执行hash校验"，第5步 rules 加"读缓存前必须验hash"。但**军师是AI不是脚本子进程**——军师"读缓存"是用 Read 工具直接读 .cache/*.md。这里有个致命区分：

- **脚本执行hash校验**（js-start.sh --check 第3步 / 未来开工读缓存逻辑）：机器执行，可靠。
- **军师自觉执行hash校验**（军师自己 Read .cache 文件时主动算md5比对）：不可靠——军师有 DET-002 形式合规前科（做了检查但走过场），很可能偷懒不验、直接用缓存内容。

方案把两者混为一谈（"军师/脚本"），没有诚实承认这个可靠性差异。这正是硬障碍2 已揭示的同一根因：**军师自动判断不可靠**。

而且 --check 每10次才跑一次（rules 第347行）。两次 --check 之间，军师每次开工若读缓存，谁来校验？若靠军师自觉，中间最多9次可能用过期缓存——DET-014"静默使用过期缓存"的风险窗口仍在。

**建议（三选一，推荐方案A）**：
- **方案A（推荐）**：缓存校验必须在脚本层执行。未来若在 js-start.sh 开工流程加"读缓存"逻辑，必须由脚本顺带算hash比对——脚本读到一致才把缓存内容输出给军师，不一致则脚本输出"缓存过期，回退读源"并直接cat源文件。军师拿到的永远是"已校验"的内容，不需自己验。--check 的缓存校验（第3步）作为兜底。rules 的"缓存使用规则"（第5步）是声明性的（告诉军师规则），但执行不靠军师自觉。
- 方案B：若坚持军师可直读 .cache，则必须在 rules 明确"军师直读 .cache 前必须先调 `js-start.sh --check-cache` 校验"——但仍依赖军师自觉调，有前科风险。
- 方案C：禁止军师直接 Read .cache 文件，缓存只通过 js-start.sh 脚本输出访问。

无论选哪个，方案必须**明确回答"谁执行校验、靠不靠军师自觉"**。当前方案回避了这个问题。

### 3.4 提醒项

**提醒1：.cache 不存在时的边界处理（DET-014变体）。** --check 第3步"遍历 .cache/*.md"，若 .cache 不存在（首次/缓存未生成），遍历应输出"无缓存文件，正常"而非报错。方案第2步已说"缓存不存在→直接读源文件"（认可），但 --check 的遍历逻辑要同样处理空目录。这是 DET-014"空返回处理"在缓存校验场景的重演，须显式处理。

**提醒2：--check 两次之间的过期窗口。** --check 每10次才跑，中间9次军师可能用过期缓存。若采用必改1的方案A（脚本每次开工校验），窗口消失；若不采用，窗口仍在。这进一步支撑方案A。

**提醒3：与 cache-intelligence-review 的路径冲突。** 见硬障碍1必改2——cache-review 写 `status/.cache/`，本方案写 `.cache/`。须统一。本方案还应同步：①修正 cache-review 第233行；②INDEX.md 登记 .cache 条目。

**提醒4：缓存校验机制的成本 vs 缓存收益。** cache-intelligence-review 已论证缓存收益是"边角"（只省读取不省思考）。现在为边角收益配套元数据头+hash计算+比对+回退逻辑+--check校验段+rules新小节——这是一套完整的过期防护基础设施。不是反对做，而是提醒老板：**这套机制的成本不低，它服务的缓存收益被高估过**。建议缓存真正落地后实测"省了多少读取时间"，对照"校验机制增加的复杂度"，如果收益仍是边角，这套校验就是"为边角收益买全险"。但老板已决定推进，本审查尊重决策，仅记录。

### 3.5 更简单的替代方案？

对于"缓存过期不静默"这个核心诉求，没有比 hash 校验更简单的等价方案——必须存储"生成时的hash"才能比对，而存储位置只能是缓存文件本身，所以元数据头是必要的。认可方案架构。

唯一的简化：如果最终采用必改1的方案A（脚本每次开工校验），则 .cache 文件不需要存 `generated_at`/`generated_by`/`expires` 这些字段（脚本每次实时算hash比对，不依赖时间过期，生成时间信息是给人看的不是给逻辑用的）——元数据头可精简为只存 `source_path` + `source_hash` 两项。但这取决于实现选择，非必须。

### 3.6 硬障碍3结论：修改后认可

hash校验+回退读源的架构正确。落地前必须补必改1（明确校验执行者，推荐脚本层执行不靠军师自觉）——这是本方案最关键的缺口，不补则 DET-014"静默使用"风险窗口仍在。处理提醒1（空目录边界）+提醒3（路径统一）。
