> 审查者：军师（Military Advisor） ｜ 审查日期：2026-08-15

> 审查依据：实际通读 `js-start.sh`/`js-end.sh`/`INDEX.md`/`js-cognitive-framework.md`/`js-cognitive-rules.md`/`js-self-review.md`/`js-cognitive.md` 后得出，非凭印象
> 结论速览：**3项认可、3项修改后认可、3项反对、1项方向认可但重定位**；原优先级排序需调整；方案前提存在与现状不符的硬伤，先纠正前提再谈收益

## 零、最重要的前置发现：方案前提与现状不符

在逐项审查前，必须先纠正一个贯穿多套方案的共同前提错误——它直接影响 P0 两项的收益估算。

### 发现1：开工加载根本没全量读 framework(40KB) 和 rules(30KB)

方案缓存2/3 声称"每次读 40KB 角度库 / 41KB 管理规则"。但 `js-start.sh` 第 [5/7] 步的实际行为是：

```bash
# 第328-333行实际代码
echo "--- 文件头（版本信息） ---"
head -15 "$COGNITIVE_FRAMEWORK"        # 只读前15行（版本+变更记录）
echo "--- 管理规则关键节标题 ---"
safe_grep "^### " "$COGNITIVE_RULES"   # 只grep节标题，不读正文
```

即：**开工时军师只读了 framework 的前15行 + rules 的节标题列表**，并没有全量加载 40KB/30KB。全量读只发生在"任务执行阶段军师主动 Read"时（整理/meta-audit/结构性变更等场景），而那些场景本来就该全量读。

这意味着缓存2/3"省30KB/35KB读取"的收益被严重高估——开工阶段根本没读那么多。

### 发现2：INDEX.md 标注与脚本行为不一致

`INDEX.md` 把 `js-cognitive-framework.md`(40KB) 和 `js-cognitive-rules.md`(30KB) 标为"每次执行"必读，但脚本实际只读头部+节标题。这是 INDEX 标注与脚本实现的偏差，本身就该修正（建议把这两项在 INDEX 里改标为"开工读头部索引，任务执行按需全量读"）。

### 发现3：60%开销的真正构成是"思考时间"不是"读取时间"

逐项拆解开销结构：
- **开工5分钟**：脚本秒级执行完，5分钟是军师"阅读+理解输出"的时间。主要花在理解 `js-cognitive.md`(8KB) + 最近自回顾 + DET表，这些是必读上下文，缓存省不掉。
- **DET自检5分钟**：DET表才11行/4.5KB。5分钟花在"逐条对照思考"，不是"读取4.5KB"。缓存省不了思考时间。
- **提案前置检查15-25分钟**：只结构性变更才做，是核心质量保障，不该省。
- **自回顾5-10分钟**：只触发条件才写。

**结论：缓存只能省"读取"，省不了"思考"。而当前开销里思考占大头。** 所有缓存方案的收益估算都建立在"读取是主要瓶颈"的假设上，这个假设不成立。收益天花板比方案预估的低得多。

这是审查的基调：不是反对缓存，而是反对"高估收益"。缓存该做，但要诚实评估它只能啃下开销的边角。

## 一、缓存类逐项审查

### 缓存1：DET快照（原P3）→ 认可但收益存疑，维持P3

**可行性**：可行。`display_det()` 已用 `awk -F'|' 'NF>=7 && $2~det'` 从 `js-self-review.md` 提取DET，快照本质就是把这8次awk的结果落盘成一次cat。

**反对收益估算**：方案说"5次awk→1次cat省30秒"。这是对开销来源的误判：
- awk执行是毫秒级，8次awk加起来远不到1秒。"省30秒"省的是什么？不是awk执行时间。
- 快照cat和awk输出的**内容一样大**（都是8条DET全文），军师**阅读时间不变**。
- 真正的DET读取优化 `js-start.sh` 已经做了——DET分层（核心层2条必读 + 场景层按`--scene`触发），script场景才加载6条场景层DET。快照是在已分层基础上再优化，边际收益极小。

**一致性**：DET变更属结构性变更类1，会触发提案前置检查。可规定"DET结构性变更后强制重建快照"，挂在Check流程后。风险可控。

**结论**：可做，但不值得为"省不到1秒的awk执行"单独维护一个缓存文件。若要做，作为 `js-end.sh` 的顺带产物（成本极低）即可，别当独立优化项。**维持P3，甚至可降为"可选不做"。**

---

### 缓存2：角度库摘要（原P0）→ 方向认可但重定位，降为P1

**可行性**：技术上可行。每个角度有标准化字段（核心问题/触发场景/领域标签/功能标签/使用次数），可机械提取为24行摘要。实测 `js-cognitive-framework.md` 确有24个角度（ANGLE-001~024），结构规整。

**纠正前提**：见发现1——开工没全量读40KB。所以摘要的价值**不在"省开工加载"**，而在"**任务执行阶段军师需要找相关角度时，先读3KB摘要定位，再按需读1-2个角度全文**"。这个收益是真实的，但定位错了环节。方案把它算进"开工加载节省"是错的。

**可靠性风险**：摘要依赖军师养成"先读摘要再读全文"的习惯。但军师有"形式合规实质失效"前科（DET-002已3次达阈值，第3轮做了数字自验却数错）。若军师偷懒只读摘要不读全文，会漏掉角度的"效果记录/可证伪条件/来源"等关键字段——而这些恰恰是判断角度是否适用的依据。摘要=信息有损，有损信息做决策有风险。

**修改建议**：
1. 摘要每行必须含"核心问题+触发场景+使用次数"三要素，缺一不可（方案已含，认可）。
2. 摘要末尾附**源文件hash校验位**，开工时 `js-start.sh --check` 比对摘要hash与framework当前hash，不一致则输出警告并降级为提示军师全量读。
3. 明确摘要只是"定位索引"，不是"决策依据"。军师定位到候选角度后，**必须**读该角度全文再决策。

**结论**：认可方向，降为P1。收益从"省30KB开工读取"修正为"任务执行时加速角度定位"。**不准当P0，因为收益依赖军师自律且有信息有损风险。**

### 缓存3：管理规则摘要（原P0）→ 反对单独建文件，合并到现有grep

**可行性**：技术上可行，但**与现有机制高度重叠，边际收益最低**。

**关键事实**：`js-start.sh` 第[5/7]步已经在 `grep "^### " "$COGNITIVE_RULES"`——这已经是一个"规则名索引摘要"了！军师开工时已能看到所有规则节标题，按节标题定位后再按需读正文。缓存3要做的"每条规则1行摘要（规则名+触发条件+一句话要点）"，和现有grep节标题的区别仅在"多一句触发条件"。

**反对理由**：
1. 现有grep节标题已覆盖80%定位需求。为多一句"触发条件"单独维护一个缓存文件，性价比极低。
2. rules才30KB，即便军师任务执行时全量读，也就一次Read。不是瓶颈。
3. 又多一个要维护一致性的缓存文件，维护成本>收益。

**修改建议**：**不单独建 `rules-summary.md`**。若要增强定位，把现有 `grep "^### "` 的输出扩展为"节标题 + 下一行的一句话"即可（grep -A1），零缓存、零一致性负担。

**结论**：反对独立立项。砍掉，合并到现有grep增强。**从P0直接砍除。**

### 缓存4：引用关系图（原P2）→ 认可方向，改为verify_refs副产品，维持P2

**可行性**：高。`js-end.sh` 的 `verify_refs()` 已经在做全量引用扫描（检查5：grep所有.md引用的.md文件名），引用图是扫描的天然副产品，不用额外开发。

**纠正收益**：方案说"Check 1从5-10次grep→1次读缓存省5分钟"。又是高估：
- grep全 `.team` 目录是秒级，不是分钟级。省的不是grep执行时间。
- Check 1交叉引用扫描的真正耗时是"军师分析影响面"，不是"执行grep"。引用图能帮军师更快理解"谁引用了谁"，这个收益真实，但不是"省5分钟grep"。

**一致性**：引用图会过期。但它的更新时机天然存在——每次收工 `verify_refs` 都跑一遍全量扫描，顺带刷新引用图即可。不需要单独的"文件变更时更新"机制（那个机制反而要检测变更，又回到hash方案）。

**修改建议**：
1. 不单独维护引用图生命周期。让 `verify_refs` 每次收工时把扫描结果写入 `ref-graph.md`（覆盖写），引用图永远等于"上次收工时的真实引用状态"。
2. Check 1用时，先读ref-graph（快），再用1次grep验证关键引用是否变化（防过期）。缓存过期≠灾难，因为有grep验证兜底。

**结论**：认可，维持P2。实现方式改为verify_refs副产品，不单独立项维护。

### 缓存5：上次执行上下文（原P1）→ 部分认可，降为P2，避免与自回顾重叠

**可行性**：部分可行，但有硬障碍。

**障碍1——内容来源不可靠**：`js-end.sh` 是脚本，它**不知道军师这次改了哪些文件**（军师是AI不是脚本子进程，脚本能拿到的只有计数器）。"修改的文件/新增的规则"要么靠军师自报（有DET-013已删除但盲区教训在：军师漏报则检查失效），要么靠git diff（**但git未初始化，ISSUE-009未解决**）。没有可靠的内容来源。

**障碍2——与现有[4/7]重叠**：`js-start.sh` 第[4/7]步已经读"最近一条自回顾"（含执行任务简述/遇到的问题/已改进/流程优化提案/历史重复次数）。缓存5要记的"任务名/修改的文件/未完成事项"大部分已在自回顾里。重复造轮子。

**修改建议**：
1. **不单独建 `last-session.md`**。要增强就在自回顾记录表里补一个"下次关注点"列（现在没有），让最近自回顾天然包含"下次关注点"。
2. 若要记"文件级变更清单"（自回顾里没有的），**前提是先解决ISSUE-009初始化git**，用 `git diff --name-only` 自动生成，不靠军师自报。git没解决前，这个缓存内容不可靠，不做。

**结论**：部分认可"快速恢复上下文"的诉求，但实现方式改为"自回顾表补列"，不单独建缓存文件。**降为P2，且绑定ISSUE-009前置条件。**

## 二、智能化类逐项审查

### 智能1：任务类型自动识别（原P2）→ 认可方向，改为"识别+可覆盖"，维持P2

**可行性**：可行。关键词匹配简单。但纯关键词会误判："整理脚本"含"脚本"会被判script（实为archive）；"审计角度库"含"审计"被判audit但可能只是查询。

**修改建议**：
1. 不完全替代 `--scene`。改为"军师自动识别作为默认值 + `--scene` 参数优先级更高 + 军师明示判断依据"。
2. 关键词规则要支持组合优先级（如同时含"整理/归档"优先于"脚本"）。
3. 识别不确定时，**军师主动向秘书确认**（呼应规则：模糊问题立即给选项追问），不静默选一个。

**结论**：认可方向，维持P2。收益是"减少手动传参错误"，不是省时间。

### 智能2：DET自检跳过无关项（原P3）→ 坚决反对

**这是10个方案里最危险的一个，必须砍掉。**

**反对理由1——拿安全网换边角收益**：DET本就是"错误转检测项"（ANGLE-022）的产物，是花钱买来的安全网。全读8条DET的阅读成本本就不高（DET表11行/4.5KB）。为省2-3分钟放弃安全网，性价比极低。

**反对理由2——DET分层已做过按需优化**：`js-start.sh` 已实现"核心层2条必读 + 场景层按`--scene`触发"。script场景才加载6条场景层DET，archive只加1条，audit只加1条。智能2是在已分层基础上再砍，边际收益小，但风险被放大（砍的是核心层DET的话就是拆安全网）。

**反对理由3——循环依赖**：方案的安全网是"执行中发现某DET相关问题时回补读"。但"发现问题"正是DET要防的——如果军师能可靠地"发现问题"，就不需要DET了。DET的存在前提就是"军师自己发现不了"。用"军师自己判断"去决定"要不要读防军师判断出错的DET"，逻辑自相矛盾。

**反对理由4——历史实证**：DET-002"形式合规实质失效"已3次达阈值，证明军师"判断哪些相关/做没做对"会出错。第3轮军师做了数字自验却数错（说7条实际8条）。把DET的执行交给军师自动判断，等于让有前科的执行者自己决定要不要自查。

**结论**：坚决反对。**砍掉。** DET全读成本可接受，不值得为省2-3分钟引入漏检风险。

### 智能3：自回顾智能生成（原P2）→ 部分认可，只自动化"事实"不自动化"反思"

**可行性**：可行。执行中维护事件清单是合理的。

**风险**：自回顾的核心价值是"军师自己的反思"（问题根因/历史重复/流程优化提案）。如果智能生成草稿，军师容易流于"审阅盖章"——而DET-002历史证明军师有"形式合规实质失效"倾向（做了检查但检查是走过场）。生成草稿+审阅可能变成走过场。

**修改建议**：拆成两半，区别对待：
1. **自动化"事实记录"**（认可）：执行中维护事件清单（哪些DET被触发/改了哪些文件/有没有被指出问题），收工时落盘。这部分是机械记录，自动化无风险，且让自回顾"有据可依"。
2. **不自动化"反思"**（反对）：问题根因分析、历史重复次数判断、流程优化提案——这些必须军师独立写。智能3只提供事实清单作为反思的输入，不生成反思草稿。

**结论**：部分认可，维持P2。明确边界：智能3=事实记录员，不是反思代笔。

### 智能4：提案前置检查智能触发（原P1）→ 认可，这是10个方案里ROI最高的，维持P1

**可行性**：高。这是唯一一个"把已规则化的东西自动化"而非"新发明判断"的方案。

**关键优势**：5类结构性变更定义明确（rules.md第416-421行），7个Check的触发条件已规则化：
- 强制层（Check 1/2/3）：每次结构性变更必做，无需判断。
- Check 4：破坏性方案（删除/归档/移除）触发——匹配操作类型即可。
- Check 5：issues.md有待审批提案时触发——检查文件即可。
- Check 6：结构性变更触发——已判断是结构性变更就触发。
- Check 7：融合/合并类触发——匹配方案类型即可。

军师不需要"智能判断Check该不该做"，只需"判断任务是否结构性变更 + 是否破坏性 + 是否融合"——这些都是**确定性规则匹配**，不是模糊判断。可靠性远高于智能2。

**与现有衔接**：`js-start.sh` 结尾已有v2.15提示（"本次任务涉及结构性变更吗"）。智能4是把这个被动提示升级为"主动判断+生成清单"，顺理成章。`js-self-review.md` 已有"复盘转化记录"表（7个Check的来源案例），可作为触发匹配的参考库。

**修改建议**：
1. 判断结果必须明示"判断依据"（为什么认为是/不是结构性变更，命中5类中哪一类），便于审阅。
2. 保留"军师可手动强制触发/强制跳过"的兜底（防误判，但跳过时必须写明理由）。
3. 生成的Check清单直接套用现有"执行证据记录"表格格式（rules.md第454-462行已定义），不另造格式。

**结论**：认可，维持P1。**这是优先推进项之一。**

### 智能5：增量加载（原P3）→ 坚决反对，架构性不适用

**方案自己已识别风险**："军师是新会话没有上次内存，即使文件没变也需要重新读。架构限制大。"

**反对理由**：这个风险是**架构性的，无法绕过**。
- 增量加载（只显示变化文件）的前提是"调用方持有上次的内存状态，只增量更新"。
- 但军师每次都是**无状态新会话**——它没有任何"上次的内存"。文件变没变，对军师来说都得从头读。
- "显示[无变化]"对军师毫无意义：军师不知道"[无变化]"的东西是什么，还是得读。
- 这套机制只对"有持久内存的长驻进程"有意义。军师是AI无状态调用，根本不适用。

**额外风险**：还要维护文件hash库，又是一致性负担。

**结论**：坚决反对。**砍掉。** 架构不匹配，投入无回报。

## 三、缓存一致性保障通用方案（审查要求5的核心回答）

所有缓存方案共享同一个致命问题：**缓存与源文件不同步怎么办？** 当前有两个硬障碍：
1. **git未初始化（ISSUE-009）**：没有git就没有可靠的"文件变更检测"和"回滚"。缓存错了无法回滚。
2. **军师无状态**：每次新会话，缓存生成在js-end.sh（脚本），但"内容来源"（军师改了啥）跨会话传递不可靠。

### 统一缓存管理原则（建议写入rules.md新增"缓存管理"小节）

| 维度 | 规则 |
|---|---|
| **谁生成** | js-end.sh脚本生成（不依赖军师记忆）。但"内容来源"分两类：①脚本可自动算的（hash/引用图/计数器）→脚本生成；②需军师提供的（任务摘要/下次关注点）→军师在自回顾里写，脚本不碰 |
| **谁更新** | 源文件变更时更新。结构性变更（5类）后**强制重建**对应缓存，挂在提案前置Check流程末尾 |
| **何时失效** | ①结构性变更后强制重建；②每次收工verify_refs时顺带刷新引用图；③js-start.sh --check校验hash不一致时标记失效 |
| **失效检测** | 每个缓存文件头部记录"源文件hash + 生成时间"。js-start.sh开工时算源文件当前hash，与缓存记录的hash比对：一致→用缓存；不一致→输出警告+降级为提示全量读（不静默用过期缓存） |
| **文件大小** | 所有缓存文件控制在绿色阈值<32KB。摘要类应<5KB。超阈值下次整理时评估 |
| **存放位置** | `.cache/`（统一路径，与.gitignore/js-start.sh/js-end.sh一致）。该目录加入INDEX.md"按需读取"区 |
| **不静默信任** | 缓存过期不等于灾难，但**绝不能静默用过期缓存**。DET-014教训：grep空返回静默=工具坏了被当没内容。缓存过期同理，必须显式警告 |

### 一致性检测的落地方式

在 `js-start.sh --check` 里增加缓存校验段（现有--check已有6项验证，加第7项）：
```
7. 缓存一致性校验：
   对每个.cache/*.md，读取其头部记录的源文件hash，
   重新计算源文件当前hash，比对。不一致→[WARN] 缓存过期，建议重建
```
复用现有 `sha1sum`/`md5sum`（纯bash依赖，符合脚本"无外部依赖"原则）。

## 四、遗漏的缓存/智能化机会

通读体系后发现两个方案没覆盖、但价值更高的机会：

### 遗漏-A：自回顾摘要索引（建议P1，比缓存5价值高）

**问题**：`js-self-review.md` 已37KB（黄色阈值），且持续增长。已有归档机制（每50次整理）。但归档后历史自回顾不可直接检索。自回顾的核心价值之一是"历史重复次数"检测（格式里有此字段），军师写新自回顾时要"翻历史看这是第几次重复"——现在靠人工翻37KB文件，低效且易漏。

**方案**：生成 `.cache/self-review-index.md`，每条自回顾1行（序号+日期+任务简述+历史重复次数+问题模式标签）。37KB→约15行<2KB。军师写自回顾时先读索引定位相似问题，再按需读对应详细自回顾。

**为什么比缓存5价值高**：缓存5（上次执行上下文）只服务"恢复上次状态"，而索引服务"检测历史重复"——后者是自回顾的核心质量功能，直接服务"根因未解决"的发现。且索引内容（序号/日期/任务/重复次数）可从自回顾表机械提取，不依赖军师自报，可靠性高。

### 遗漏-B：历史重复自动检测（建议P1，智能类的真金子）

**问题**：自回顾格式要求"翻js-self-review.md历史记录，本问题是第几次出现。>1次说明根因未解决"。但军师靠人工翻历史判断"第几次"，容易漏（DET-002就是"形式合规实质失效"3次才达阈值——说明前几次没被及时识别为重复）。

**方案**：军师写自回顾时，基于遗漏-A的索引，自动检索历史自回顾中相似的问题模式（关键词/问题类型匹配），提示"这可能是第N次重复，上次出现在序号XXX"。军师审阅确认。

**为什么比智能2/3价值高**：智能2是砍安全网（有害），智能3是代笔反思（有风险），而历史重复检测是**增强安全网**——让"根因未解决"的发现更早更准。这正是ANGLE-022"错误转检测项"闭环的关键一环，且判断依据是历史记录匹配（有据可查），不是模糊判断。

**两者关系**：遗漏-A（索引）是遗漏-B（检测）的基础设施。先建索引，再赋能检测。

## 五、修订后的优先级排序

### 砍除项（3个）
- **缓存3 管理规则摘要**：与现有grep节标题重叠，砍掉，合并到grep增强。
- **智能2 DET自检跳过**：拿安全网换边角收益+循环依赖，砍掉。
- **智能5 增量加载**：架构性不适用（军师无状态），砍掉。

## 七、总结（给老板的一句话推荐）

**先纠正前提再谈优化**：当前方案的P0两项建立在"每次全量读40KB角度库+41KB规则"的错误前提上，实际 `js-start.sh` 已只读头部+节标题。缓存的收益天花板受限于"读取只占开销的小头，思考占大头"，被普遍高估。

**推荐落地顺序**：
1. 先初始化git（解ISSUE-009）——这是所有缓存的前置条件。
2. 推智能4（提案前置检查智能触发）+ 遗漏-A（自回顾索引）——这俩是P0，ROI最高且可靠。
3. 砍掉智能2（DET跳过）、智能5（增量加载）、缓存3（规则摘要）——一个有害、一个不适用、一个重复。
4. 其余按修订排序推进，每个落地后实测真实节省，不靠预估。

**核心立场**：缓存和智能化该做，但要诚实——它们啃的是开销的边角（读取），啃不动大头（思考）。别指望靠缓存把60%开销降下来，那是误导。真正的开销大头在"思考"和"必读上下文理解"上，那是认知成本，缓存省不掉。
